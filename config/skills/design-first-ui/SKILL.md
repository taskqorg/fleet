# Design-first UI

Use this skill for Fleet when the project places the work in the [Design-First workflow](../../../docs/design-system/README.md#design-first). The project contract records the rollout state. This skill does not apply to other projects or nonvisual work. The designer and implementer run `node scripts/ui-context.ts <page>` and read the owner principles first. The designer follows steps 1–4; the admitted implementer uses the existing sealed selection and follows step 5 without requesting a second choice. A reviewer reads the supplied page context, checks the evidence required by the relevant stage and reports gaps, without designing or deciding.

1. In managed Chromium, walk the live section and navigation neighbours with real data in dark and light at 1440×900 and 390×844. Record deployed version, routes, observed cases, and code, data and missing-field differences. Call out unobserved cells. Map the operator job, its entry points and returns, affected surfaces and states, and the owner of each reusable composition or control.
2. In task-private source, build one to three meaningfully different options from Fleet's actual UI package. Keep fixture data, shell and review states comparable. A restoration still needs an explicit rendered option and selection. Use a private copy of the pinned project source with canonical scene paths. Keep proposed production behavior outside this stage. Use one shared component for each repeated composition or control in the scene and product, with fixture or live data and actions supplied by the caller. Identify the shared owner and any part not yet shared. When changing a control, consult the official SDK and Solid guides matching the versions in the project lock; record the versions, relevant guidance and any unavailable source.
3. Use the [capture command](../../../packages/ui/book/README.md#capture) for each affected state. Open all original PNGs at their actual size. Look at first scan target, reading order, grouping, spacing, alignment, truncation, action and state visibility, focus and touch. Compare against the baseline and neighbours. Fix findings and recapture. Retain a critique for each frame with the rule or trade-off it illustrates. Before offering a choice, exercise the affected actions, navigation and return on every affected surface, including restored focus and scroll position; label simulated or unavailable actions and unobserved behavior.
4. Submit the exact recipe, four stored originals per state, live observations and critique for Fleet to seal. The addressed owner choice selects one option or requests rework. A task acceptance, chat answer or an unsealed artifact is insufficient.
5. After Fleet admits the production stage, transfer the selected scene, implement the approved behavior, and verify the normal app routes and states against the four-frame references. Material visual differences return to design. Check the exact PR and queue candidates and repeat the real-data walk after deployment, exercising the same actions and returns on every affected surface and checking restored focus and scroll position. Keep the sealed approval originals and recipe immutable: a shared-component change needs a new capture and, for a material difference, a new owner decision.
