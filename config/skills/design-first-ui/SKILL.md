# Design-first UI

## Browser for Fleet visual QA

In Fleet, use managed Linux Chromium through `project-browser` for visual QA and the protected verifier’s isolated Linux Chromium for protected checks. Never launch or fall back to user-installed macOS Chrome, including Playwright `channel: "chrome"`. If the required Linux browser is unavailable, record the affected check as unverified. This rule also applies outside native design admission.

## Native design workflow

Follow these steps only for Fleet visual work in the [Design-First workflow](../../../docs/design-system/README.md#design-first). The project contract records the rollout state. The designer and implementer run `node scripts/ui-context.ts <page>` and read the owner principles first. The designer follows steps 1–4; the admitted implementer uses the existing sealed selection and follows step 5 without requesting a second choice. A reviewer reads the supplied page context, checks the evidence required by the relevant stage and reports gaps, without designing or deciding.

1. In managed Chromium, walk the live section and navigation neighbours with real data in dark and light at 1440×900 and 390×844. Record deployed version, routes, observed cases, and code, data and missing-field differences. Call out unobserved cells. Map the operator job, its entry points and returns, affected surfaces and states, and the owner of each reusable composition or control.
2. In a private copy of the pinned source, build one to three meaningfully different options from Fleet’s UI package at canonical scene paths. Keep production changes outside the design stage. Before rendering, pin the comparison scope, normal route and state, viewport and theme, and deterministic synthetic responses at the coordinator operation boundary for all options. For whole-viewport approval, render the actual application shell on the normal route before showing the options to the owner. Demo wrappers with substitute navigation cannot qualify production chrome. Bring any proposed change to the agreed comparison contract to the owner. A restoration still needs an explicit rendered option and selection. Use the same shared component in scene and product, with fixture or live data and actions supplied by the caller. Identify its owner and any part still separate. For control changes, consult official SDK and Solid guides matching the installed versions in the lock and record the versions, relevant guidance and unavailable sources.
3. Use the [book capture procedure](../../../packages/ui/book/README.md#capture) for standalone scenes. For whole-viewport originals, follow the [normal-route capture and sealing requirements](../../../docs/design-system/README.md#design-first). Leave the choice pending while a reproducible normal-route capture or sealable recipe is unavailable. Open every qualifying original PNG at actual size and critique the first scan target, reading order, grouping, spacing, alignment, truncation, action and state visibility, focus and touch. Compare against the baseline and neighbours, fix findings and recapture. Retain a critique for each frame with its rule or trade-off. Before offering a choice, exercise the affected actions on every affected surface. Record runtime checks separately from frame comparisons, including navigation, return route, restored focus and scroll position. Label simulations and gaps. The reviewer independently checks return, focus and scroll against the pinned scope.
4. Submit the exact recipe, four stored originals per state, live observations and critique for Fleet to seal. The addressed owner choice selects one option or requests rework. A task acceptance, chat answer or an unsealed artifact is insufficient.
5. After Fleet admits the production stage, transfer the selected scene, implement the approved behavior, and verify the normal app routes and states against the four-frame references. Material visual differences return to design. Check the exact PR and queue candidates and repeat the real-data walk after deployment, exercising the same actions and returns on every affected surface and checking restored focus and scroll position. Keep the sealed approval originals and recipe immutable: a shared-component change needs a new capture and, for a material difference, a new owner decision.
