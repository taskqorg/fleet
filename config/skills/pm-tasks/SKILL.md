# Tasks

Perform authorized work directly with native tools when useful; delegation is optional. Apply this task lifecycle when the work needs Fleet tracking.

1. Read first: `task_page {filter: {search}}` for a task that already covers the request, `project_context` for the project. Do not create a duplicate; update the existing task instead.
2. Write the task with `task_create`: a short title; `expectedOutcome` says what is done, why, how to check it and where the result goes (`resultDestination`). An agent's task starts Held. If creation returns a pending request key, read the original outcome with `agent_tool_result {requestKey}` and do not repeat the mutation while its outcome is unknown. After creation is confirmed:

   - In a taskless non-bot conversation that belongs on the task thread, use `session_task_attach {taskId}`. Creation alone does not attach the conversation.
   - In a bot conversation, Fleet links tasks created in the bot's project to its managed tasks. Use `bot_task_link` for existing work in that project when needed. In a problem conversation, record the task code or pull request URL with `problem_update {id, work}`. All bot conversations are ineligible for task attachment.

3. Refine the task with `task_update` (title, expectedOutcome, priority, resultDestination) while it is Held.
4. Release authorized work with `task_release` without redundant confirmation. Follow the [Fleet visual handoff](#fleet-visual-handoff) before releasing visual work in that workflow. Preserve explicit holds; ask when a substantive decision or missing authority requires it. Use `task_hold`, `task_release` and `task_cancel` for execution control; cancelling keeps the history. Acceptance is separate (step 8).
5. Before dispatch, set the project focus and enable `pm-watch` for execution, task and question changes. Fleet starts a worker for every queued task that nothing has started (the project's `worker` role, the task as its first message, ordinary placement); `task_get` shows the run, or a `waitReason` such as `no worker role` when it cannot start. Do not start a second worker for it. End your turn. Confirmed completion, failure or stop wakes the creating session; an unconfirmed outcome needs watch observation, not a completion assumption.
6. For file results, worker text must require `artifact_save {path, name, required:true}` on a regular file with a link count of one. Use a worktree-relative path or an expanded absolute path under the worktree, the run's `$TMPDIR` or `$FLEET_INPUT_DIR`. Avoid symlinks below those roots and `..` components. If ordinary `/tmp` is refused, copy the file into the run's `$TMPDIR` and pass the copy's expanded path. Then use `artifact_list` and `artifact_get {artifact_id}` to download the retained copy. Require the worker to compare the downloaded bytes with the original before reporting success. A save acknowledgment or metadata alone does not verify bytes. Only after verified retention may the worker remove its own generated output files, and only when they are not required workspace deliverables; never discard source edits, pre-existing files or unpushed work. Report artifact IDs and byte-check evidence. Leave files intact on unavailable or unconfirmed retention.
7. Read the result with `execution_status {sessionId}` and `task_get {taskId}`, then report it to the person in a few lines: outcome, evidence, what is left. For `task_get`, use the task UUID from the `id` field of a `search` task hit or `task_page` row. If you have a display code such as `T-FLT-42`, use it to find the task first. For a blocker or question about an existing task, use `ask {taskId, question, requestId}` so the same question appears on the task and in this conversation; this does not attach a multi-task PM session. Omit taskId only for a session-only question.

8. Inspect retained artifacts with `artifact_get` and verify their downloaded bytes yourself when native tools are available, or use a worker's byte-check evidence. If verification is unavailable, request it without claiming acceptance. Do not equate a nonempty artifact list or successful execution with acceptance. Under the person's explicit acceptance authority, call `task_request_acceptance {taskId, artifactIds}` (or use its existing acceptance question), then `questions_answer {questionId, answer:"accepted", artifactIds}` only after the required checks pass. Otherwise present the evidence and ask the person to decide. Read back task acceptance and selected artifact IDs; there is no `task_accept` operation.
9. Acceptance queues cleanup for inactive task sessions. Inspect the teardown outcome; queued cleanup or archival is not proof of removal. After a session is inactive, `session_archive {sessionId}` requests teardown, including for failed trials. Preserve uncommitted changes, unpushed commits, failed teardown and unknown execution state; report the keep reason rather than bypassing safeguards. Keep task-thread attribution: attached PM work belongs in task totals; unavailable cost is unknown, not zero.

## Fleet visual handoff

In Fleet’s [native design workflow](../../../docs/design-system/README.md#design-first), declare visual impact before any writer starts. If the PM has several projects in scope, select authorized Fleet focus with `focus_set {projectIds: ["fleet"]}`. Before releasing a Held task, confirm its authorized designer is linked so a bare release cannot auto-start a writer. If needed, create an idle designer session without a task or first message and call `session_task_attach` with that designer’s `sessionId` and the task’s `taskId`. After release, send the idle designer its first brief with `message_send`, explicitly targeting its `sessionId` with a stable `requestId` and nonempty `text`. Use `session_get` to confirm the linked designer execution or its concrete wait. A design-only task ends at the owner’s choice, with no implementation writer enrolled.

When the same task explicitly authorizes implementation and live verification, record the concrete check in `completionRequirements.liveCheck` at creation or in an `expectedOutcome` line of the form `Landing: wait — live check: <check>`. Read it back with `task_get` before enrolling the writer. After release, inspect linked sessions and executions and reuse an eligible project-authorized writer, including one Fleet already started. Start a writer only when the coordinator cannot auto-start a competing one. For a new writer, use `session_start` with the same `taskId`, the authorized writable role and branch, a stable `requestId`, and nonempty `text` telling the writer what to implement after admission and what to verify live.

Read the linked writer’s execution state and `waitDetail` with `session_get`. Before the first offer, confirm the writer is pending behind native admission. When placement is available, admission waits for a sealed offer and then for the owner’s selection. Use `design_review_get` to read an existing offer or selection. With an existing selection, check the writer’s execution separately for admission or its concrete wait. Fleet supplies the selected sources on admission. Check the task’s open questions separately and verify that any superseded generic recovery question clears. Keep delivery open through the live check.
