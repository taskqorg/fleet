# Tasks

Perform authorized work directly with native tools when useful; delegation is optional. Apply this task lifecycle when the work needs Fleet tracking.

1. Read first: `task_page {filter: {search}}` for a task that already covers the request, `project_context` for the project. Do not create a duplicate; update the existing task instead.
2. Write the task with `task_create`: a short title; `expectedOutcome` says what is done, why, how to check it and where the result goes (`resultDestination`). An agent's task starts Held. After receiving its ID, link this conversation with `session_task_attach {taskId}` if it has no task; creation alone does not attach it. A failed or pending acknowledgment is not proof that creation failed: use `agent_tool_result {requestKey}` for the original call and do not repeat the mutation while its outcome is unknown.
3. Refine the task with `task_update` (title, expectedOutcome, priority, resultDestination) while it is Held.
4. Release authorized work with `task_release` without redundant confirmation. Preserve explicit holds; ask when a substantive decision or missing authority requires it. Use `task_hold`, `task_release` and `task_cancel` for execution control; cancelling keeps the history. Acceptance is separate (step 8).
5. Before dispatch, set the project focus and enable `pm-watch` for execution, task and question changes. When delegation is useful and no pipeline picks the task up, start a worker: `session_start {projectId, requestId, role: "worker", taskId, hostId, text}`. Use the requested host ID from `hosts_list`; omit hostId only when placement is unrestricted. End your turn. Confirmed completion, failure or stop wakes the creating session; an unconfirmed outcome needs watch observation, not a completion assumption.
6. For file results, worker text must require `artifact_save {path, name, required:true}`, then `artifact_list` and `artifact_get {artifact_id}` to download the retained copy. Require the worker to read and compare those downloaded bytes with the expected result before reporting success. A save acknowledgment or metadata alone does not verify bytes. Only after verified retention may the worker remove its own generated output files, and only when they are not required workspace deliverables; never discard source edits, pre-existing files or unpushed work. Report artifact IDs and byte-check evidence. Leave files intact on unavailable or unconfirmed retention.
7. Read the result with `execution_status {sessionId}` and `task_get`, then report it to the person in a few lines: outcome, evidence, what is left. For a blocker or question about an existing task, use `ask {taskId, question, requestId}` so the same question appears on the task and in this conversation; this does not attach a multi-task PM session. Omit taskId only for a session-only question.

8. Inspect retained artifacts with `artifact_get` and verify their downloaded bytes yourself when native tools are available, or use a worker's byte-check evidence. If verification is unavailable, request it without claiming acceptance. Do not equate a nonempty artifact list or successful execution with acceptance. Under the person's explicit acceptance authority, call `task_request_acceptance {taskId, artifactIds}` (or use its existing acceptance question), then `questions_answer {questionId, answer:"accepted", artifactIds}` only after the required checks pass. Otherwise present the evidence and ask the person to decide. Read back task acceptance and selected artifact IDs; there is no `task_accept` operation.
9. Acceptance queues cleanup for inactive task sessions. Inspect the teardown outcome; queued cleanup or archival is not proof of removal. After a session is inactive, `session_archive {sessionId}` requests teardown, including for failed trials. Preserve uncommitted changes, unpushed commits, failed teardown and unknown execution state; report the keep reason rather than bypassing safeguards. Keep task-thread attribution: attached PM work belongs in task totals; unavailable cost is unknown, not zero.
