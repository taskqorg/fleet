# System

**Status.** Built, rail section System ([information architecture](../../designs/fleet-ia-and-journeys.md#1-closed-information-architecture)): one view (`app/src/views/hosts.tsx`) renders every System route; the earlier paths `/hosts`, `/hosts/limits`, `/keys`, `/runners`, `/spend` and `/humans` redirect. This spec is the section frame; the content of each root keeps its own spec: [Hosts and limits](hosts.md), [Runners](runners.md), [Spend](spend.md).

**Purpose.** Are hosts, accounts, connections and spend healthy, and who has access? [Live](live.md) answers "what runs now"; System is where the person configures and repairs.

**Routes:**

| Route | Opens |
|---|---|
| `/system` | Idle: readiness and spend summary |
| `/system/hosts/<name>` | One host: state, workers, readings, CLIs, accounts and models, store, Remove |
| `/system/hosts/new` | Add host (`hosts_register`) |
| `/system/accounts`, `/system/accounts/<id>` | Accounts & limits; one subscription |
| `/system/connections/<id>` | One connection: keys, access, intake, balancing, limits |
| `/system/connections/new` | Add connection (`connections_create`) |
| `/system/access` | Access: every subscription, model key and service key with its state and next step; the add flows |
| `/system/runners` | CI runners and agent runs per host |
| `/system/problems`, `/system/problems/<code>` | Problems: every open problem with its owner bot and phase; the opened problem with its owner's conversation |
| `/system/agents`, `/system/agents/<class>` | Agents: what agents could not do, one row per class, and the opened class with its finding |
| `/system/spend` | Spend: period, total, breakdown, what it bought |
| `/system/people/<id>`, `/system/people/new` | One person and their access (owner only) |
| `/hosts…`, `/hosts/limits`, `/keys…`, `/runners`, `/spend`, `/humans…` | Redirect to the matching System route |

## Layout

Three columns ([OR-24](../owner-rules.md)). Shell header: title, the section's action for the open root as an icon (Add host, Add connection, Invite person), focus chip, search.

* **Control column** (`CatalogueTree`, [OR-48](../owner-rules.md)): one tree with the roots **Problems, Access, Hosts, Accounts & limits, Connections & keys, Agents, Runners, Spend, People** (People only for the owner), no mode switch ([OR-46](../owner-rules.md)). Problems, Agents, Runners and Spend are roots without children: a click opens their page. A host leaf: state icon (red only for a dead or failing host, [OR-56](../owner-rules.md)), name, and on the right running of slots and last seen ([OR-22](../owner-rules.md)). An account leaf: harness mark, name, left of capacity as a small gauge.
* **Work area, idle:** readiness first: hosts with a problem, accounts near their limit, connections with failing keys, each as one [problem row](../controls/problem-row.md) with its fix action, repeats as `×N` ([OR-58](../owner-rules.md)); then today's and the month's spend as figures with the link to Spend; then services with errors in the last hour. A healthy System says so in one line.
* **Work area, a host open:** the host's stacked [detail sections](../controls/detail-section.md) as [Hosts](hosts.md) specifies, with "Show on Live" in the head.
* **J5 compatibility** ([journey J5](../../designs/fleet-ia-and-journeys.md#3-core-user-journeys-j1j5)): an account inspection (`account_connect`) probes the models the host's vendor CLI offers that binding (codex `model/list`, Claude Code `initialize`); a run that fails because the vendor does not know its model marks the model rejected on that binding until the next probe. The router skips a binding for a model it is known not to serve (cause `subscription:<id>:model:<model>`); a binding whose list is unknown is never skipped. The host page lists **Accounts and models** with the probe's age and a problem row per profile no account there can serve; the account page shows the models per host in **Runs on**, **Profiles on this account** one row per model, and **Router skips, 24 h** (`route_decisions` with `subscriptionId`); idle readiness has one row per profile no ready binding anywhere serves.
* **Spend figures** carry a [sparkline](../controls/figure-tile.md), one bar per UTC day from `spend_summary` with `by: day`: the last 12 days on the idle screen (Spend today, Unpriced runs), the chosen period on Spend (Total, Runs, Unpriced usage). Cost per task and Tasks done have no daily read and no sparkline.
* **Add host** (owner or full access) and **Add connection** are the shell header's plus on their root; each opens its form in the work area (OR-14). Add host sends the SHA-256 printed by `scripts/host-secret.sh` on the host; without it Fleet mints a secret, shown once on that page and kept nowhere in the browser. Add connection opens the new connection's page, where its key is added.
* **Not built: held by Balancing.** The board draws an Access row in the state "held by Balancing". Balancing is not built and waits for the owner's decision; the row state comes with it.
* **Work area, Access** (approved 2026-11-25, board frame "System › Access: status and onboarding (approved)"; `app/src/views/access.tsx`): the head counts what works, what needs the owner and what is not added, with **Add access** and **Check all**. Three groups (subscriptions · login on a host, model API keys · credits, services), one row each: name and kind, a state badge (family `access`) with its sentence, limit or credits, where it serves and how many profiles use it, the last check's age (red when it failed) and one next-step button (Sign in on a host, Paste a key, Add a provider, Check billing, Check). Then the browser-only Ultra items as links. **Add an API key:** provider and connection name, then the numbered steps with the key and billing pages, a password field (sent once to `connections_key_add`, never shown again) and **Add and check**, which shows the check's state and, on a failure, the billing link. **Sign in:** host, then **Sign in on <host>** starts the vendor login on that host (`access_onboard` kind login `start`); the link and device code the host printed appear here within seconds, the host waits up to 15 minutes, then **Check** reads who is signed in. **Limit:** amount, unit and month for a connection (`access_onboard` kind limit). Checks are read-only and never start a login. Data: `access_status`, `access_check`, `access_onboard`; the list paints from the read mirror and the change stream rereads it (no timer; a gateway pass that records a connection's calls is a change of that connection). Only Sign in rereads every 3 s until the host shows its link.
* **Access, Servers** (approved 2026-11-26, board frame "System › Access: servers and project grants"; `app/src/views/access-grants.tsx`): a fourth group, shown once a project server is added ([project access](../../designs/fleet-project-access.md)). One row per server: server, address, via (its jump server), state (enrolled with the fleet-provision version, not enrolled, or failing with the check's error) and the pinned host key's SHA-256 fingerprint. A row opens its detail under it (`/system/access?server=<id>`; that link scrolls the row into view and focuses it at every width): the whole fingerprint with Copy, the last check and its steps, **Check** (`access_server_check`) and the server's live grants, each linking to its project's Access facet. **Enroll** (approved 2026-11-26, board frame "System › Access · server not enrolled: enroll command"): a server not enrolled, or running another fleet-provision version, shows to a full-access person the hint (run once as root on its address; behind a jump server, reach it with `ssh -J root@<via address> root@<address>`), the enroll command in two lines with an ellipsis, **Copy command** (the whole ~18 KB line), Check and the command's size; others see that it is not enrolled. The list never scrolls sideways: in a narrow work area each server is two lines (name and state; address · via · host key, the last check's age last). Data: `access_grants` (with `enroll`), reread by the change stream (kinds `access-server`, `access-grant`).
* **Access, Local agents** (approved 2026-11-26, board `local-agents.bl`; [local agents](../../designs/fleet-connections.md#13-local-agents)): a fifth group, always shown to the owner and full-access people, with **Connect a local agent**. One row per machine and harness: the harness and machine, a state badge (connected, needs a refresh, unused, disconnected) with its sentence, the connections count and the last successful call's age. A row opens its detail: one line per connection with its last successful call and last failure, the drift line with the command to run, **Refresh** (`local_agent_connect`) and **Disconnect**. Connect: pick the machine (the person's hosts) and the harnesses, then one command per harness with Copy; the row turns connected after the command's check calls.
* **Agents** (approved 2026-11-26, board `drafts/agent-garden` frames 1, 2, 4, 5; `app/src/views/agent-gaps.tsx`): its own list and detail. The list: failed runs, failed gateway calls, findings open, changes being watched and not classified over the window; Host, Agent and Window picks; one [gap row](../controls/gap-row.md) per class, most failures first. The opened class (idle: the first class with a finding, UR-35): the step trail; before/after once the change reached every host, else one line saying who failed how often with the decisive line; the finding's problem with its owner bot and phase, linking System › Problems where the person talks to the bot; Investigation (the owner bot's problem conversation); What changed (the linked pull request, its stage, what the finding waits for); Where (failures per host); Controlled by (the setting and what a fix there does); Examples (agent on host, the decisive line, the day, linking its conversation or task). Data: `agent_gaps` (view; the change stream rereads it), `delivery_history {number}` for the pull request, `problem_get`. Phone: the list; an opened class fills the screen.
* **Problems** (approved 2026-11-26, board `drafts/anomaly-routing` frames B and E; [routing rule](../../designs/fleet-system-management.md#problems-anomalies-with-a-bot-owner)): the head counts open problems and their owners ("33 problems · HAL0 owns 31 · PM fleet 2 · none without owner"). Groups in this order, each a group head with its count: Stuck (attention), Without owner (danger), Agent working, Escalated, Watching, New; New and Fixed today fold into one line naming the first classes. A row: the problem in words with `×N`, under it its subject and the owner's latest note; on the right the owner bot, the phase as a [status pill](../controls/status-pill.md) in words (Stuck, Agent working, Fix in review #n, Watching, New, Escalated) and the time of the last change last ([OR-64](../owner-rules.md)). No buttons on a row. The opened problem (idle: the first stuck, else the first working, UR-35): title with `×N`, subject, owner and phase; the owner's problem conversation (subject `problem:<id>`) and its [composer](../controls/composer.md), which writes to that bot. Data: `problems_list`, `problem_get`, the conversation's messages; the change stream rereads on kind `problem`. Phone: the list; an opened problem fills the screen with its conversation.
* **Work area, Spend:** the [Spend](spend.md) page; cost is shown here because it is the question ([OR-54](../owner-rules.md)).

## States

* **Unconfirmed host:** "running · unconfirmed, last seen 4m", never failed (UR-32).
* **Risky action** (remove a host, rotate a key, change money): starts only from a confirmation card naming its scope and the way back ([OR-61](../owner-rules.md)).
* **Phone (390 px):** the tree; an opened item fills the screen.
* **Person, Telegram** ([canvas](../board/screens/people.bl)): the person card has a Telegram section (`TelegramLink`, `app/src/views/humans.tsx`). Not linked: the Telegram users who wrote to the bot without a link (`telegram_people.unknown`), each with Link, then a typed user id, the language (English, Русский) and Link; the bot confirms the link in that chat. Linked: the state, the @username and id, the language as a choice that saves at once, when it was linked (time last, [OR-64](../owner-rules.md)) and Unlink. The People list adds the @username after the email. Machine identities have no Telegram.

## Review of the current build

Checked against the [product map](../product-map.md) rows for System.
* **Keep:** everything the root specs describe for one host, limits, connections and keys (`/keys`), people and access (`/humans`, with the Cloudflare Access state), CI runners and Spend.
* **Change:** release and harness-pin drift shows on each host instead of on Changes; the idle screen leads with problems to fix.
* **Drop:** the spend table on Runners (Spend is the one place for cost, [OR-54](../owner-rules.md)); the "updated 40s" page head on Hosts (the offline marker covers it); services without errors on the idle screen (only services with errors in the last hour show).
