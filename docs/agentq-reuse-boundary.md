## AgentQ: actual public boundary

`runtime/src/lib.rs` exports agent, archive, cli and installation, and aliases coreq process/quiet/telemetry internally. `runtime/src/agent.rs:15-39` keeps adapter, stdio, native, events and protected modules private while re-exporting Launch, Policy, Run, Runtime and protected host types. The Codex `AppSession` itself is **pub(crate)** in `runtime/src/agent/registry/codex/app.rs:24`; its apparently public methods are not a separately accessible public session library.

The ordinary public path is Runtime/Launch/Run. `adapter.rs:100-135` exposes Policy and pre-spawn/spawned callbacks. `Run` around 406 includes process/run state, event cursor, native rollout progress, ownership/activity, frozen results and archive handle; record around 516 consumes telemetry Context/Store. It is not a bare JSON-RPC channel.

The protected public path is `ProtectedHost`, `ProtectedPreparation`, `ProtectedAppServer` in `agent/protected.rs`. It verifies an executable hash and optional signed adapter identity, constructs host prepare/launch/observe/cancel requests, and verifies slot/permit protocol. Public receive/send/open/reply methods around 165-242 are useful for an already-adopted protected-host architecture. They are not an authority-free escape hatch into AppSession. Bringing that path into Fleet would introduce another host/permit protocol to reconcile with Fleet's existing executor trust and grant records.

### Defaults are not Fleet defaults

Policy derives Default. Scope, Network and Approval default to **Native**; tools=None preserves native tools; isolated/subscription/unelevated booleans default false (`adapter.rs:67-117`). No default guarantees Fleet's cleared environment, dedicated homes, subscription-only account, disabled discovery or never-prompt policy. Configure/Spawned hooks allow a caller to supply process setup; they do not prove a safe setup happened.

`adapter.rs:624-653` chooses protocol operation for instruction/MCP/control requirements. It sets developerInstructions explicitly, but accepts ordinary MCP transport fields only command/args/env and then adds **server-wide default_tools_approval_mode=approve**. That cannot represent Fleet's current narrow request_child approval unchanged. The lower AppSession passes caller thread parameters through and never approves a server request itself. These are different layers and must not be conflated.

### Why AppSession is not currently a small extractable package

Verified dependencies in `app.rs` include `use super::*`, parent Spec/native scope/process helpers, NativeFrame from private stdio, runtime event/model/limits/history types, sampler/process attribution, archive JournalRecord and record(Context, telemetry::Store). Checkpoint serialization mixes protocol state with root/home/scope, model/usage/windows/process data. `stdio.rs:16-40` mixes raw/parsed frames with optional archive records and caller process hooks; dropping its handle explicitly does not kill an active session. A verbatim two-file copy does not close these dependencies.

An upstream extraction is technically plausible **as a refactor**, not available as a current public API: separate request IDs/pending state, handshake, thread/turn correlation and terminal facts from transport, history projection, recording and sampling. Inputs would be explicit open/turn parameters and native frames; outputs would be outbound messages and correlated facts, with no grants, config discovery or durable admission. Existing AgentQ could adapt its history/recording outside that core. Feasibility follows from those identifiable responsibilities, but no build or refactor proof was performed. It would require changes and qualification in AgentQ as well as Fleet, so it is not necessarily the shortest path to Fleet's next bounded qualification.

## Concrete Fleet boundary

**Fleet keeps:** trusted host/execution identity; effective profiles and grants; HOME/CODEX_HOME and subscription provisioning; session/workspace/native-thread mapping; commands/outbox and result routing; child relationships; cancellation authority; artifact immutability/diffs; unknown-outcome reconciliation; existing process ownership and resource labels.

**Native mechanism owns:** framed local JSON-RPC I/O; initialized handshake; explicit thread/start or thread/resume; explicit developerInstructions and current settings at that boundary; one correlated turn/start; inbound request refusal/allowed response handling; raw notifications plus terminal/interrupt facts. It has no permission to create a Fleet child, retry a logical task or replace a missing native thread on its own.

For Codex, one mechanism for fresh and resumed sessions avoids duplicate policy/event/lifecycle implementations. The thread-open method and retained ID differ; the rest can be shared. This is a protocol-specific implementation behind Fleet's existing executor, not a general multi-agent framework. Claude and other harnesses should retain separate native implementations; AgentQ's descriptors, Orca's adapter contract and T3's ProviderAdapterV2 illustrate a common product-facing boundary without equating different native instruction/stop semantics.

This updates the earlier report's preference for investigating extraction: AgentQ need not become a dependency. The useful reuse is explicit developer-role mapping, correlation/recovery invariants, process-close semantics and existing test scenarios. Do not judge total complexity by added line count alone; a tiny wrapper with new lifecycle ambiguity is worse than a slightly larger direct client with clear ownership. Orca and T3 remain recurring implementation references; their Electron/product or Effect/orchestration closures are not needed dependencies for Fleet's Rust executor.
