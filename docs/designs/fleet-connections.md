# Fleet connections

API key connections provide service access through Fleet's gateway. Subscription accounts remain separate; both use the holder, access, intake and budget model in [people and access](fleet-people-access.md). The coordinator registry is `go/coordinator/connections.go`, provider catalogue `providers.go`, gateway `go/gateway`, and connection MCP client `go/executor/mcp_connection.go`.

Tools use granted connections; pipeline definitions contain no credentials or account-selection logic. Multiple methods may share a connection. Attribute each call, usage and failure to the work that consumed it; unavailable quota or usage remains unknown. Shared accounts do not gain a separate quota on each host ([allocation](../work-allocation.md)).

Account switching and method substitution are distinct. Another eligible account is used automatically only under configured rules. Method changes follow [selection and fallback](../configuration.md#discovery-selection-and-fallback); an explicitly selected method is not silently replaced. Resolve uncertain prior outcomes before retrying. Operators see affected work, interruption cause and continuation actions; architects see usage, availability and configuration. Continuation may use another authorized account, wait for quota recovery or select another method.

## Glossary

- **API key connection:** a named provider binding with holder, access, intake, tools and budgets.
- **Key:** a secret identified by fingerprint; state `active`, `draining`, `disabled` or `retired`.
- **Gateway:** the separate `fleet-gateway` process on PDS18; only it sends provider key values to providers.
- **Snapshot:** coordinator-published token hashes, access lists, provider catalogue and key states; no key values.
- **Spool:** append-only gateway call records ingested by the coordinator.
- **Per-run token:** bearer minted for one execution, removed when the execution ends.
- **Tool:** a provider operation exposed by a connection.
- **`tool_run`, `connection_cost`:** one API call and its usage/cost measurement.
- **`fleet-machines`:** the Access service token used by executors to reach PDS18.

Subscription logins never pass through the gateway. It does not hold or relay OAuth/session credentials. Key switching must not bypass quotas; 429 and quota replies pass through. No Fleet-invented queue bound or rate is added; an owner may configure one per connection. Model API keys as harness endpoints remain a separate, unbuilt integration.

## Technical Plan (Architecture)

Agents reach `fleet-executor mcp connection`, coordinator API steps call HTTP in-process, and both send the execution's token to `fleet-gateway`. The gateway reads the last valid snapshot, attaches the provider key, and appends the call to its spool. The coordinator ingests that record into one accounting execution; caller-supplied labels are not authority.

### 1. Model

*   **`provider`**: a code-side catalogue entry, not a table: `{id, baseUrl, tools: {<tool>: {method, path, unit, idempotent}}}` in `go/coordinator/providers.go`. Tavily exposes `web_search` → `/search` and `web_extract` → `/extract` (unit `credits`, idempotent); Meshy exposes submit and job-read tools. The coordinator copies the catalogue into the snapshot, so the gateway has no second copy.
*   **`api-connection`** document kind (separate from subscription accounts): `{id, name, provider, holder, access: {people: [], projects: [], experiments: []}, intake: all | paused, tools: [], comment}`. **Use:** a run token gets the connection when the run's director, its project or its experiment is listed (any one is enough); `projects: ['*']` means every project; empty means only work directed by the holder. **Visibility** is separate from permission to use a connection; metadata reads follow the normal operation and project scope gates, without exposing key values.
*   **`connection-key`** document kind: `{id, connectionId, fingerprint (first 12 hex of SHA-256), state, addedAt, addedBy, disabledReason?, disabledAt?}`. No value. The key's id is its fingerprint (document id `key:<fingerprint>`), so the gateway's disabled-key file and the spool name keys the same way.
*   **Delete.** `connections_delete {connection}` (owner or full-access person; agents are denied it) removes a connection once every key is retired: the connection row, its key rows, its history (an audit row `deleted-connection:<name>` stays) and its value directory. Run tokens drop its name and open key requests for it are withdrawn, so a new connection of the same name inherits nothing. An active, draining or disabled key refuses it (409).
*   The connection carries `holder`; key operations resolve it through `connectionId`, using the same holder/owner and audit model as subscriptions.

### Anthropic operations

The `anthropic` catalogue entry uses native [Messages](https://platform.claude.com/docs/en/api/messages/create) and [Models](https://platform.claude.com/docs/en/api/models/list) at `https://api.anthropic.com`. Fixed headers are `x-api-key` and `anthropic-version: 2026-10-21`, per [authentication](https://platform.claude.com/docs/en/api/overview#authentication) and [versioning](https://platform.claude.com/docs/en/api/versioning). Keys requiring an explicit workspace header are unsupported.

- `create_message`: non-idempotent `POST /v1/messages`; requires `model`, positive integer `max_tokens` and nonempty `messages`. Optional fields: `system`, `metadata`, `stop_sequences`, `tools`, `tool_choice`, `thinking`, `output_config`, `cache_control`, `service_tier`, `stream: false`. Anthropic validates native nested content and model-specific parameters. Streaming and other top-level fields are refused before sending. Callers cannot select headers or a URL. Native JSON replies retain existing secret redaction.
- `list_models`: idempotent `GET /v1/models`; only query parameters `limit` (1–1000), `after_id`, `before_id`. Returns one native page; omitted pages and failed reads do not establish availability.
- Messages usage is `tokens`: reported input + output + cache creation + cache read tokens. Missing input/output or malformed counts leave usage unavailable; absent/null cache counts contribute zero. Other usage and breakdowns remain in the native reply. This sum is not a price or billing weight; no Anthropic price or per-key reconciliation is supplied.
- Existing key-pool rules below apply: quota/429 passes through without switching; 401/402 disables only the selected key. Uncertain Messages calls never replay, including HTTP 5xx whose completion remains unknown. This does not promise another client's failover behavior.

### 2. Keys

*   **Values.** `<FLEET_SECRET_DIR>/connections/<connection>/<fingerprint>` on PDS18, one value per file, mode 0600, coordinator user. Added through `connections_key_add` (owner or full-access person only), which writes the file and the metadata row in one step and returns only the fingerprint. Screens, agents, executors and profiles never receive a value.
*   **Key requests.** An agent (a PM session through its Fleet tools, or any execution through the project tool of the same name) calls `connections_key_request {requestId, connection, reason}`. It opens a question of kind `secret` for the owner, with options `{connection}`, idempotent by `requestId`; an agent's question is tied to its execution, so it also shows in that conversation. The owner sees it under Needs you, on its task and in the conversation as a password field with Add key and decline. Add key sends the value from the browser to `connections_key_add {connection, value, questionId}`, which stores it as above and, in the same transaction, answers the question with the JSON text `{connection, fingerprint, state}`; the agent reads that answer with `question_history`. A value Fleet already holds as an active key of that connection answers the request too. Rules: only the owner or a full-access person answers, never an agent, even one acting with the owner's rights; the answer must name an active key; any other answer than `decline` or that fingerprint text is refused, so a typed answer cannot carry a value; the request takes no other argument, so no value rides in it; agents are denied `connections_key_add`; the key row records `addedBy`. The API keys screen (`/keys`, Architect) adds a key without a request.
*   **Import and restore.** At start the coordinator registers every value file that has no row, if the file name matches the value's fingerprint and the connection is held by the owner or a full-access person (such as `site-agents`); another holder's files are skipped with a log line; a directory named after a catalogue provider with no connection becomes that connection (holder owner, access `{projects: ['*']}`). `scripts/connections-import.sh` splits a one-key-per-line file into such files, so import and restore need no database step.
*   **Gateway load.** `fleet-gateway` runs as a user unit of the coordinator user, which already owns the secret directory, so a separate service user would protect nothing. It reads a key's value file when a snapshot first names the key and checks it against the fingerprint; a key change takes effect at the next snapshot adoption, with no restart. Restarts drain in-flight calls while the socket stays open (socket activation).
*   **Backup.** The secret directory is encrypted with SOPS/age into the nightly backup (`fleet-backup.sh`, `secrets.sops.json`; recipient `FLEET_BACKUP_AGE_RECIPIENT` in `backup-age.env`, the age identity kept off the host). To restore, decrypt with the age identity, start the gateway, it serves from its retained snapshot without Postgres.
*   **Rotation:** add → mark old `draining` (no new calls) → `retired` after the owner confirms. Only the owner or a full-access person may re-enable a disabled key; its holder may retire it without re-enabling it. A retired key stays retired. No quiet-period timer (no invented number).
*   **Key balancing & failover (`keyPolicy`).** Configured per connection with `connections_set_key_policy {connection, keyPolicy}` (holder or owner; replaces the object as a whole, omitted fields return to defaults). By default (`keyPolicy` absent), selection is `sticky` and failover occurs only when a key gets no HTTP answer **and** the tool is `idempotent` (a non-idempotent tool such as Meshy submit returns `outcome: unknown`, never replayed), while 429 and quota replies pass through unchanged with `Retry-After`. Opt-in `strategy` supports `sticky` (default), `round_robin` (rotates across usable keys on each call), and `least_used` (picks the lowest `recorded + in-memory` usage with round-robin tie-breaking). Opt-in `failoverStatuses` (HTTP `400..599`, e.g. `[429, 432]`) cools down the failing key (`Retry-After` if positive seconds, at least `cooldownSeconds` default 60; else `quotaCooldownSeconds` default 3600 for 432; else `cooldownSeconds`) and retries the next candidate within the same non-multipart call (or returns the provider response unchanged if it was the last candidate); when all active keys are cooling down, the gateway refuses with `503 all-keys-cooling-down` and `Retry-After`. Re-enabling a key (`enabledAt`) clears its cooldown. 401 and 402 disable that key (persisted in the gateway's `disabled-keys` file and reported in the spool, failing over to the next live candidate when `failoverStatuses` is configured on a non-multipart call); a 403 passes through and is recorded on the key as a visible problem with the provider's message, never disabling it (a tool with `forbiddenIsCall` passes it through without recording it), so one bad request body cannot take out the keys one by one (owner decision); a plan or credit limit (Tavily 432 and 433) is recorded the same way with its status, and System › Access shows it as an account problem ("credits are used up", next step: top up or upgrade the plan) until a later call succeeds (when it is the only active key); if none is left, `503 no-usable-key`.
*   **Reconcile** (Tavily first): every 10 minutes the coordinator asks the gateway's `GET /v1/usage` (loopback, not routed by Caddy, and bearer = the coordinator's per-process usage token whose hash is in the snapshot), which asks the provider per key (catalogue `usage: {path, field}`, Tavily `/usage` `key.usage`). The first answer is the key's baseline; later ones compare the provider's usage since the baseline with the credits recorded for that key's `tool_run` rows since then. A positive difference ("another client uses this key") shows on the key; a failed report shows as unknown, never as a match. Current limitation: a failed gateway request, non-2xx reply or invalid top-level report retains the prior observation without recording the new failure ([tracked correction](https://github.com/taskqorg/fleet/issues/325)); it is not fresh reconciliation proof.

### 3. Gateway

*   **Code.** `go/gateway` is independent of the coordinator and Postgres so coordinator restarts do not stop calls. It provides snapshot adoption, disabled-key persistence, provider error mapping, spool and loss counter:
    *   route `POST /v1/call/<connection>/<tool>`, generic over the provider catalogue;
    *   auth by per-run token hash from the snapshot, without caller-supplied attribution labels;
    *   keys read from the secret directory by fingerprint, so no restart on a key change;
    *   a re-enabled key comes back when the snapshot's `enabledAt` is later than the local disable;
    *   every reply carries `x-fleet-call-id`; a gateway refusal also carries `x-fleet-error` (a passed-through provider reply is `http-<status>` to the client);
    *   no fixed queue bound; a bound is added only when the owner asks for one;
    *   needs-you questions are grouped by cause (people-access §7), for example `key:<id>:disabled`;
    *   budget flags from the snapshot refuse calls with `budget-reached`;
*   **No database on the request path.** The gateway reads `snapshot.json` every second, and once more at once when a call carries a token hash it does not know, before refusing it with `unauthenticated` (this closes the gap between minting and adoption). At most one such reread runs at a time, so junk tokens cannot force a reread storm. The coordinator writes the file atomically on every change of tokens, access lists or key states. A missing or invalid file keeps the last valid one; `/healthz` reports its age. Schema (`GatewaySnapshot` in [`contracts/gateway.schema.json`](../../contracts/gateway.schema.json), one Go type in `go/contract` for the writer and the reader):

    ```text
    {schema: 2, generated_ms, providers: {<id>: {baseUrl, tools, usage?}},
     connections: {<name>: {provider, tools, intake, keys: [{id, state, enabledAt?}], blocked: [<scope>]}},
     tokens: [{sha256, executionId, directedBy, projectId, experimentId, connections: [<name>]}], usageTokenSha256}
    ```
*   **Spool.** `<FLEET_GATEWAY_DIR>/state/spool/<day>.jsonl` (UTC day), append-only; a past day's file is deleted after the coordinator has ingested every line of it; a past day's file with a line that cannot be imported (not a `CallLine`) is kept and logged on each pass, for the owner to inspect and remove. One JSON line per call (`CallLine` in the same contract; absent fields are omitted): `{callId, tokenSha256?, executionId?, connection, tool, keyFingerprint?, status, errorCode?, outcome: ok | error | unknown, usage?: {unit, amount}, disabled?: {key, status}, keyProblem?: {key, status, message}, providerAttemptAt?, transfer?: {direction, bytes, mediaType, name, sha256?}, phase?: started | completed, startedAt, ms}`. A file call carries `transfer`; a download or resumable upload commit writes two lines with one `callId` ([§9](#9-files)), and ingest updates the row by `callId` when the `completed` line arrives. The coordinator's in-process call (`api` steps) returns the same type, with `output` (the provider's reply) added. The coordinator ingests it every few seconds (and at step completion) into `tool_run` rows with `connection_cost`. Ingest is idempotent by `callId`; a persistent `lost` counter shows lines that could not be written.
*   **Reach.** Loopback `127.0.0.1:8742` on PDS18. Other hosts call `https://fleet.ufobe.com/v1/call/...`: the Access app "Fleet gateway" (path `/v1/call`) admits only the `fleet-machines` service token, and Caddy sends the path to the gateway, which checks the run token.

### 4. Per-run tokens

*   When dispatch writes the start command, the coordinator mints a random token for the execution, stores its SHA-256 with `{executionId, directedBy, projectId, experimentId, connections}` and republishes the snapshot. The executor receives it in the start command (stored with the command row until the run ends) and writes it, with the gateway URL and the Access file path, to a private run file `<FLEET_DATA_DIR>/runs/<executionId>.env` (0600, in a 0700 directory), deleted when the run ends. Each connection MCP server gets that file's path as its last argument (`fleet-executor mcp connection <name> <spec> <run file>`) and reads `FLEET_RUN_TOKEN`, `FLEET_GATEWAY_URL`, `FLEET_CF_ACCESS_FILE`, `FLEET_WORK_DIR` and `FLEET_INPUT_DIR` from it (the last two are the run's work and input folders for [file tools](#9-files)); the harness environment carries none of them.
*   **Threat model.** A token attributes calls per run. It does not isolate runs of one OS user from each other: under FD5 all runs of one harness account share an OS user, so one run can read another live run's environment (`/proc/<pid>/environ`) and call with its token until that run ends. On a held host, the holder can do the same. Both stay within that token's connections, and the holder already sees everything on their host. One OS user per run would close it (data foundation A15 rejected that for now).
*   The token's connections are the profile's granted connections filtered by each connection's `access` list and intake. `projects: ['*']` means all work, with or without a project (Lab runs have none).
*   The coordinator's connection tick (every 3 s) ingests the spool, then marks the tokens of ended executions revoked and republishes the snapshot, so recovery and every other ending path are covered; no separate expiry number. An `api` step's token is revoked right after its call. An execution that ends while the coordinator is down keeps its token until recovery settles it; the first snapshot after that removes it. A grant revocation removes tokens too (people-access §3). Child executions get their own tokens.
*   Coordinator-side `api` steps get a token for their step execution the same way.
*   **Not built: script steps with gateway tokens.** The target gives a token for their step execution the same way, with the profile-free grant set of the pipeline step's `connections` list. The executor writes the same run file and passes its path as `FLEET_RUN_FILE`; the script calls `POST /v1/call/<connection>/<tool>` with it. Each call is a `tool_run` child of the step, so a script that calls the gateway twice records both calls and both costs.
*   **Owner connection tokens.** The owner's own interactive sessions (Claude Code, Codex, Hermes on any host) use a long-lived token from `connections_token_create {name, connections}` (owner and full-access people such as site-agents during development, the minting person recorded as `directedBy`; the value is answered once, with the MCP spec). It lives in a 0600 file named by `FLEET_TOKEN_FILE`, never in a session config. The session runs the same Go client as Fleet runs, `fleet-executor mcp connection <connection> <spec>` with `FLEET_GATEWAY_URL` and `FLEET_TOKEN_FILE` in its environment; scripts use `fleet-executor connection call`. The tick keeps it; `connections_token_revoke` ends it. Its calls are `tool_run` rows with no parent run and `data.tokenName`, directed by the owner. Such a token may name a [project access](fleet-project-access.md#how-agents-use-a-grant) connection when its minting person sees every project the connection is open to. `connections_token_set {name, connections}` changes a live token's connections with the same checks and keeps its value; `scripts/dev-connections.ts <token> <claude|codex> [connection ...]` runs it and registers the answered specs as the harness's MCP servers, the one way a host's dev sessions gain a connection.

### 5. Call methods

*   **HTTP:** `POST /v1/call/<connection>/<tool>`, body the tool's JSON, `Authorization: Bearer <run token>`. Replies use (`unauthenticated`, `bad-request`, `no-usable-key`, `key-disabled-<status>`, `provider-unreachable`, `provider-body`, `provider-timeout`, and the file codes of [§9](#9-files); provider status passes through). `x-fleet-outcome` names the gateway's outcome, and the client follows it.
*   **Pipeline calls:** the coordinator makes `api` step calls in-process over HTTP with the step's run token. A call answers one `CallLine` (`contract.GatewayCall`, shared with the executor's connection MCP server): `{tool, connection, callId, status, outcome, errorCode?, output}`; error classification (`infra:`/`unknown:`/`step:` problems in fleet-lab.md) stays.
*   **MCP:** `fleet-executor mcp connection <connection> <spec>` (`go/executor/mcp_connection.go`), one stdio MCP server per connection; the start command's `connections: [{name, instructions, tools: [{name, description, inputSchema, file?, idempotent}]}]` gives the spec, so hosts need no connection files. `file` picks the transfer mode and `idempotent` how an edge error reads ([§9](#9-files)); the server keeps both out of `tools/list`. The executor adds it to each run's MCP config and allowlists `mcp__<connection>__<tool>` (`go/executor/executor.go`).
*   **CLI:** `fleet-executor connection call <connection> <tool> [spec file]` reads the arguments as JSON on stdin and prints one `CallLine` as JSON (exit 1 when the outcome is not `ok`), with the MCP server's environment. With a spec file (one spec, a list, or a `connections_token_create` reply) a file tool uses its file mode; without one the tool is called as JSON.
*   **Path fields.** A `{field}` in a catalogue path takes that body field and leaves the body. Before the path's `?` the value must match the tool's `pathPatterns` entry (or be a plain id) and is inserted as is; after the `?` it is query-escaped, so a free-text value (a YouTrack search) cannot add or end a parameter.
*   A tool marked `textReply` in the catalogue passes a 2xx reply that is not JSON as `{"text": ...}`, so the JSON-only clients read it (Bugsink's Markdown stacktrace, [error tracking](fleet-error-tracking.md#4-agent-read-access)).
*   The gateway spool is the accounting record; an agent-authored local call file is not accounting authority.
*   **Built-in web** stays off unless the profile says `web_route: builtin` (fleet-lab.md R3.4).

### 6. Accounting and budgets

*   Prices for `estimated` money live in the price table ([fleet-analytics.md](fleet-analytics.md#price-table)); a catalogue tool with a fixed vendor price gets its entry with its catalogue entry. A typed-decision provider (yes/no and pick-one answers with probabilities, unit `input_tokens`) is one such catalogue entry.
*   Every call: `tool_run` execution, parent = calling execution, `directed_by` and project copied from the token, plus a `connection_cost` measurement `{connection_id, amount, unit, basis}`. A call on a coordinator read token (`<connection>-read:<uuid>`) also gets `system_actor = coordinator`: it is [system activity](fleet-analytics.md#system-activity), counted by its connection but not as the project's work. Basis `measured` when the provider returned usage, `estimated` when Fleet computed it from the price table, `subscription` for a subscription run, `unavailable` otherwise ([basis list](fleet-analytics.md#price-table)).
*   Budgets use the shape in people-access §9 with `scope = connection` or with the connection named in a person, project or experiment budget. Spend reaches the coordinator through spool ingest, so a `pause` or `stop` budget can be overshot by the calls made during the ingest delay plus calls in flight, and without limit while the coordinator is down (the gateway keeps the last flags but cannot count). The coordinator computes reached budgets and writes a "blocked by budget" flag per (connection, scope) into the snapshot; the gateway refuses such calls with `budget-reached`, and keeps the last flags while the coordinator is down. Dispatch applies the same budgets to agent runs. `warn` never refuses.
*   Lab usage units are `calls` and `credits`.
*   **Connection budgets.** `budget_set` with `scope: connection` counts that connection's `tool_run` rows, system activity included: unit `calls`, or the amount of the provider's own unit (`credits`), optionally per `period`. The action is a setting with default `warn` (owner rule outside Lab): `warn` and `pause` show on the budget and the person can ask for more; only a reached `stop` connection budget, set by the owner, becomes `blocked: ['connection']` in the snapshot on the next tick, and the gateway answers `budget-reached`. The gateway also refuses a run whose `person:`, `project:` or `experiment:` scope is listed; person, project and experiment budgets that name a connection are not built yet. `budget_ask {budgetId, limit, reason}` raises one question (`budget:<id>:ask`); only the owner's `approve` writes the new limit, audited with both people.
*   **Meshy.** Catalogue tools `image_to_3d` (not idempotent), `job_status` (`GET .../{jobId}`: a `{field}` in a catalogue path takes that body field) and `recent_tasks`. The job step maps Meshy's task (`status`, `model_urls`, `consumed_credits`) to the job shape; the credits land as `connection_cost` when the task succeeds. Meshy submit has no idempotency key: it is never retried or failed over. On an unknown outcome or 5xx, read the key's `recent_tasks` (`sort_by=-created_at`) and adopt only one matching task created around the call start, not already owned by another execution and with matching image input when the provider returns it. The current matcher allows 5 seconds before the recorded start for clock tolerance. With no matching task, several matches, or unreadable recent tasks, finish `unknown:submit-unconfirmed` and send nothing again. The adopted provider job ID stays in `execution.data.jobId` (the Connections Q1 recovery path).
*   **Asset providers.** Meshy `multi_image_to_3d`, `multi_job_status` and `multi_recent_tasks`; providers `huggingface` (`inference`) and `google-ai` (`generate_content`, `interaction_create`, `interaction_get`, `models_list` ([§10](#10-google-ai-ultra-and-antigravity)), key in `x-goog-api-key` by the catalogue's `keyHeader`, usage from `usageField`). Meshy `job_status` and `multi_job_status` report `consumed_credits` when `status` is `SUCCEEDED` (`usageWhen`), keyed by `usageOnce: jobId`; spool ingest counts it once per (connection, job), later polls cost 0, and a pipeline step's job is counted by its step instead. A `{field}` path value is checked against the tool's `pathPatterns` before a key is attached. `scripts/key-add.sh <connection>` sends `connections_key_add` with the value read from stdin only. Keys move from the owner's Mac Keychain this way, csgo tools call the gateway, and each Keychain copy is deleted after the first good call and a backup listing its fingerprint ([asset pipelines §1](fleet-asset-pipelines.md#1-keys-and-providers-s1)).

### 7. Deleting Pipe (stage C4)

Fleet has no Pipe bridge or dual accounting path. The gateway replaces its read lane; subscriptions remain outside it. Deployment cleanup and the archived AssetQ service are covered by [infrastructure](../infrastructure-build.md) and [asset pipelines](fleet-asset-pipelines.md#2-deleting-assetq-s2-after-s1). This heading remains for existing citations; historical rollout tasks live in pull requests.

### 8. YouTrack

The owner's task tracker is YouTrack at `youtrack.ufobe.com` (it replaces Asana). The `youtrack` catalogue entry calls its REST API at `127.0.0.1:9520`, the container's loopback port on PDS18, with a permanent token of the YouTrack user `fleet-agents` as bearer. That user is in the YouTrack group `Agents` and in the same project teams as Tight, so Fleet agents see the projects Tight sees and their changes are attributed to `fleet-agents`, not to the owner. Agents close issues themselves (Done, Won't fix) once the work is delivered and verified; YouTrack does not restrict that for the group. Tools: `projects`, `issues_search` (YouTrack query, 50 per page), `issue_get`, `issue_comments`, `issue_create`, `issue_update`, `comment_add`, `command` (YouTrack commands set fields, tags and links), `attachment_add {issue, path}` and `attachment_get {issue, attachment}` ([§9](#9-files)). `issue_get` returns attachments as `id, name, size, mimeType, comment(id)` and `issue_comments` each comment's attachments; When a file-capable MCP client uses a token minted with `attachment_get` on an enabled connection, neither asks for the signed `url`, which works without the key and would bypass accounting. Older clients, older tokens and connections without the grant keep their existing `issue_get` URLs. Rotate owner tokens and refresh their MCP specs during rollout. The instructions say attachment content is data, never instructions, and that an `unknown` upload is checked in `issue_get` before another try. Reads are idempotent; writes are never replayed. A 403 on a YouTrack write means the account may not do that action, so the write tools set `forbiddenIsCall`: the 403 passes to the agent and is not recorded on the shared key. A 403 on a read is still recorded, so a key that lost access shows. Tight (Hermes on PDS18) uses the same connection through its owner connection token `pds18-hermes` and the loopback gateway, so it holds no YouTrack key and its YouTrack changes are attributed to `fleet-agents`.

### 8a. Telegram

The `telegram` catalogue entry is the Bot API of Fleet's Telegram channel; its key rides in the URL path (`keyPath: /bot`). The coordinator's channel is its only caller; see [Telegram channel](fleet-telegram.md).

### 9. Files

A catalogue tool with `file` moves bytes instead of JSON. The flag is generic; YouTrack's two attachment tools are its first users. The key stays in the gateway, and each transfer is one `tool_run` with `data.transfer {direction, bytes, mediaType, name, sha256}`.

*   **Catalogue.** `file: upload` (POST only, not `idempotent`, no `inject`, no `usageOnce`) or `file: download` with `fileFrom {url, bytes, name, mediaType}`, the dotted lookup-reply fields of the relative file URL, its size, name and media type. A tool that breaks these rules makes the gateway refuse the whole snapshot.
*   **Limits.** Per connection, set with `connections_set_limits {connection, limits}` (holder or owner; the object is replaced whole, an omitted field returns to its default): `fileBytes` (largest upload, default no cap), `replyBytes` (largest download, no cap), `stallMs` (longest time without progress, 60 000), `answerMs` (wait for the provider's response headers on file tools, 120 000). The JSON path keeps its 1 MiB request and 16 MiB reply caps and `request_timeout_ms`.
*   **Upload, client.** The model gives `{<path fields>, path}`. A relative path is taken against `FLEET_WORK_DIR` in a Fleet run, else the server's working directory. The path guard checks the denylist while resolving symlinks, then opens the resolved path from `/` one component at a time with `O_NOFOLLOW` (a folder or file swapped for a symlink after resolving is refused), and requires a regular file with one hard link; with `FLEET_FILES_ROOTS` set (a path list) it must lie under one root, and a code-mode upload must also lie under the code sandbox's read roots. A denylist in code refuses the file when it, or a folder opened on the way, is by device and inode one of: the run file and its folder, `FLEET_TOKEN_FILE`, `FLEET_CF_ACCESS_FILE`, `FLEET_HOST_SECRET_FILE`, the stores of the executor data folder (`FLEET_DATA_DIR` or the default: `journal.sqlite` with its WAL files, `runs/`, `spool/`, `accounts.json`; its sessions and worktrees stay uploadable), and under the home folder `.config/fleet/` (tokens, specs, host secret, the coordinator's key directory), `.local/share/fleet/gateway/` (gateway state), `.ssh/`, `.aws/`, `.gnupg/`, `.netrc`, `.config/gh/`, `.hermes/.env`, `Library/Keychains/`, `.claude/.credentials.json`, `.codex/auth.json`, `.git-credentials`, `.config/git/credentials`, `.docker/config.json`, `.kube/config`, `.npmrc`, `.pypirc`, `.config/gcloud/`, `.gemini/oauth_creds.json`, `.azure/`, plus `$CLAUDE_CONFIG_DIR/.credentials.json` and `$CODEX_HOME/auth.json` (`path-refused`, naming the entry). In a Fleet run HOME is the harness's home, so the run file also names the executor user's home (`FLEET_USER_HOME`, the same home entries) and the executor's own stores (`FLEET_RUN_DENY`, a JSON list: its data folder stores, host secret, Codex account, account registry and each registry account's native home and login files, the Git connection directory, the forge's GitHub store, the artifact store's config and key file, and the browser bindings with each project's Access file), and carries the executor's `FLEET_FILES_ROOTS`. No root is forced by default (isolation helps, not forbids). The first pass writes a private unlinked copy, hashes the copied bytes and scans them across read boundaries for the caller's bearer and Access secret. The exact name sent to the gateway gets the same scan (`secret-in-file`; nothing is sent). The second pass streams only the checked copy: `POST /v1/call/<connection>/<tool>`, `Content-Type: application/octet-stream`, exact `Content-Length`, `X-Fleet-Args` (base64url JSON of the path fields, `name` = the base name of the opened file (a symlink gives its target's name), with characters the gateway refuses replaced by `_`, and `mediaType` from a fixed extension table or the first 512 bytes), `X-Fleet-Sha256`, `Expect: 100-continue`.
*   **Resumable upload.** HTTPS clients stage files over 4 MiB in requests of at most 4 MiB on the same call route. The client first probes with `X-Fleet-Upload-Mode: status`, then sends `chunk` with `X-Fleet-Upload-Offset` and finally `commit`. Each request repeats the raw upload fields and adds `X-Fleet-Upload-Id` (Unix seconds and a random nonce) and `X-Fleet-Upload-Size` (whole-file bytes). The gateway binds the ID for the token to one route, arguments, size and digest once it confirms the first chunk. Acknowledgments report the durable `X-Fleet-Upload-Offset`. Replaying a chunk reports that offset. After a cut or a gateway restart, the gateway drops any unconfirmed tail and the client resumes from the confirmed offset. The gateway checks free space against each chunk or raw upload, concurrent write reservations, and 64 MiB of filesystem headroom. An old gateway can refuse the initial status probe and the client can use the raw route.
*   **Commit and cleanup.** Only a complete staged file with a matching SHA-256 and a clean full-file secret scan can reach YouTrack. The gateway records the call ID, syncs a `started` spool line (`unknown:upload-unfinished`), and atomically marks the commit. It rechecks authorization and the current size cap immediately before the provider POST. A restart before the mark can resume the commit with the original call ID. Drain before handoff preserves the stage. The `completed` line carries any provider usage and key effects once. Replaying a retained spool can apply those effects if an older coordinator completed the row during rollback. A refusal records the provider attempt's time so replay respects a subsequent key re-enable. Repeated commits for the same ID return an unknown outcome with the original call ID and create no second POST or spool entry. After an unknown commit, compare attachment name, size and SHA-256 before attempting another upload. Terminal commits and explicit aborts remove staged bytes. An authenticated caller can abort its own stage while intake is paused. The gateway durably marks a discarded stage before removing data or recording the pending commit's known failure. Gateway startup and maintenance can recover the failure from saved call attribution without a new request. A premature commit preserves the confirmed prefix. Interrupted stages survive restart and expire after one day, as do their commit records; expired IDs cannot start or replay a transfer.
*   **Upload, gateway.** The tool is resolved before the body is read; refusals come first (`file-expected`, `length-required`, `file-too-large`, `bad-request`, `bad-file-name`). The body is staged under `state_dir/files`, counted, hashed and scanned (with the name) for every key value the gateway holds and the caller's bearer, with `stallMs` per read. A short body, `stalled`, `sha-mismatch`, `secret-found` or `staging-failed` reaches nothing. Then one multipart part goes to the provider with the key, the reply is redacted as for JSON, the spool line carries `transfer`, and the staged file is removed.
*   **Download.** The client sends the JSON path fields with `Accept: application/octet-stream`. The gateway looks the file up with the key, refuses a URL that is not a path on the provider's own host and a size over `replyBytes` (before the fetch), fetches the URL without the key and without following redirects, writes a `phase: started` spool line (outcome `unknown`, `download-unfinished`, fsynced) before the response headers, streams the bytes unredacted with `X-Fleet-File {name, mediaType, bytes}`, and writes a `phase: completed` line (`ok` with the sha256, or `download-cut`, `client-stalled`, `provider-stalled`). A short provider body aborts the caller's connection, so a cut is never a short file that ends cleanly.
*   **Download, client.** The file goes to `<root>/<path fields but the last>/<last>-<name>`: `<FLEET_INPUT_DIR>/attachments/TGT-12/85-1234-screen.png` in a Fleet run, else under `FLEET_FILES_OUT` (default `~/.local/share/fleet/files`). The root (the run's input folder or `FLEET_FILES_OUT`) is trusted; every folder below it (`attachments`, the issue) is opened inside an `os.Root`, created 0700 when missing, and refused when it is a symlink (`path-refused`), as is a final name that is not a regular file. The file name `<prefix>-<name>` has `/`, `\`, control and bidi characters and a leading `.` replaced by `_` and is cut to 200 bytes. The bytes go to `<name>.<random>.part` in that folder (`O_EXCL`, 0600), are counted, hashed and fsynced, then renamed over the final name through the original root if the folder is still there in the same folder; any failure removes the part file (`download-cut`, `client-stalled`, `write-failed`). The result is `{path, name, bytes, mimeType, sha256, callId}`; an upload's is `{reply, name, mediaType, bytes, sha256, callId}`.
*   **Client timeouts.** No total deadline. `FLEET_STALL_MS` (default 60 000) bounds each wait for progress in either direction and a JSON call's wait for headers; `FLEET_ANSWER_MS` (default 180 000, above the gateway's `answerMs`) bounds the wait for headers after the last byte of a file call's request (for an upload plus the time its body took, since the gateway posts the staged file on before its own `answerMs` starts). The minted spec carries a connection's set `stallMs` and `answerMs`, and the client waits at least `stallMs` and `answerMs` plus a minute, so the gateway answers first; an owner token's spec is the one returned at its creation. The executor passes its own `FLEET_STALL_MS` and `FLEET_ANSWER_MS` to its runs through the run file.
*   **Edge errors.** A 5xx without `x-fleet-call-id` came from Cloudflare or Caddy: `edge-<status>`, `unknown` for a tool that is not `idempotent`, `error` for one that is or when the upload body never left whole. A connection lost before the last upload byte is `error` `upload-interrupted` (the gateway posts only a whole, checked file); lost after it, `unknown` `connection-lost`.
*   **Drain.** Unchanged (35 s, `TimeoutStopSec=45`). On stop, uploads still staging or staged but not posted are refused (`draining`, or a reset that the client reads as `upload-interrupted`); posts in flight finish within the drain or end `unknown`.
*   **Pipelines.** A pipeline `api` step that names a file tool fails with `file-tool-unsupported` before any call: only the host client moves files.
*   **Tripwires, not data-loss prevention.** Both scans look for exact values; a base64, compressed or encrypted copy passes.

### 11. Access status and onboarding

One read shows every subscription login, model API key and service key Fleet has or offers, and how to add what is missing (System › Access, approved on the board `screens/system.bl`). Agents use the same operations; a person never needs a shell or a checklist (`go/coordinator/access.go`).

A connection makes its provider's cheapest call (models list, balance, or one search credit for Tavily) with a coordinator read token, recorded as a `tool_run`; a subscription queues a status inspection (`account_connect`) of each host binding. ### 12. Grants drift

A connection gets the provider's catalogue tools when it is created; a tool added to the catalogue later is not granted
to connections that already exist. On 2026-11-26 the github connection lacked six tools the coordinator reads, and
those reads went to the keyless public GitHub API, which answered 403 for hours. The grants drift check compares
grants with uses (`go/coordinator/grants.go`).

*   **Uses.** A tool is needed on a connection when coordinator code calls it there (`gatewayUses`: the code path,
    the provider and the connection that serves it; `TestGatewayUsesListed` keeps the table in step with the code),
    when an agent profile lists the connection (every catalogue tool; `project-access` counts for each project access
    connection), or when a coordinator call on it was refused with `unknown-tool` (the calling file and line).
*   **`connections_drift`** (architect, agent tool): per connection the granted tools, the catalogue, the needed tools
    with their users, the missing ones, stale grants the catalogue no longer has, the key policy and pool (active and
    all keys), and the last audited settings change (field, actor, time, the operation that writes it).
*   **Problem.** A pass every 2 minutes (`FLEET_GRANTS_TICK_MS`) asks one problem per connection with a missing tool
    (cause `problem:grant:<connection>`), naming each tool, its users and the fix `connections_set_tools`. It closes
    after two passes without the gap.
*   **No silent fallback.** A GitHub read the gateway refuses with `unknown-tool` fails with that cause instead of
    reading the public API; a refused key (expired, wrong lifetime) still falls back to the public repository.

## Failure and recovery

- Gateway or PDS18 unavailable: calls fail; agent execution may continue without them. A separate gateway avoids coupling calls to coordinator restarts.
- Missing/invalid snapshot: keep the last valid snapshot and expose its age in `/healthz`; new tokens cannot work until adopted. Ended runs may retain tokens while the coordinator is down, until reconciliation publishes revocation.
- Uncertain charged calls are not replayed. Failover requires an idempotent tool and no HTTP answer.
- A spool write failure increments the persistent loss counter. Unimportable past-day records are kept for inspection.
- The same OS user can read another live run's token; see the per-run threat model. Token attribution is not per-run OS isolation.
- Budget overshoot includes ingest delay and in-flight calls, and is unbounded while the coordinator is down.
- A deploy during a transfer: an upload cut before the provider stage is a clean `error` (`draining` or `upload-interrupted`; staging discarded, nothing sent) and may be retried. An upload cut during the provider post is `unknown`: the agent reads the issue's attachments (name, size, and `attachment_get` plus sha256 when needed) before trying again. A cut download is `download-cut` and may be repeated; its row stays `unknown: download-unfinished` when no completed line was written.

## Verification

Existing boundary tests are `go/gateway/gateway_test.go`, the client tests in `go/contract/gateway_call_test.go` and `go/contract/gateway_upload_test.go`, the staging tests in `go/gateway/upload_resume_test.go`, and the path guard tests in `go/executor/file_guard_test.go`. They protect secret-free replies/snapshots, token attribution/revocation, holder/access gates, failover, usage, spool retention, and for files every refusal code, the path guard, the tripwires, the download folder, and two-phase accounting for downloads and resumable commits. A provider 403 is recorded on the key and **never disables it**; 401/402 disable it. Tests use fake providers; a docs rework does not call providers or mutate real keys.

Backup encryption is implemented by `deploy/infrastructure/fleet-backup.sh`; a backup listing alone is not a restore proof. A restore check needs the encrypted secret directory and the off-host age identity, then verifies a clean gateway can read its retained snapshot and restored values without Postgres. No restore or production key rotation is implied by editing this specification.
