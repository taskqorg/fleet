# Fleet connections

API key connections provide service access through Fleet's gateway. Subscription accounts remain separate; both use the holder, access, intake and budget model in [people and access](fleet-people-access.md). The coordinator registry is `go/coordinator/connections.go`, provider catalogue `providers.go`, gateway `go/gateway`, and connection MCP client `go/executor/mcp_connection.go`.

Tools use granted connections; pipeline definitions contain no credentials or account-selection logic. Multiple methods may share a connection. Attribute each call, usage and failure to the work that consumed it; unavailable quota or usage remains unknown. Shared accounts do not gain a separate quota on each host ([allocation](../work-allocation.md)).

Account switching and method substitution are distinct. Another eligible account is used automatically only under configured rules. Method changes follow [selection and fallback](../configuration.md#discovery-selection-and-fallback); an explicitly selected method is not silently replaced. Resolve uncertain prior outcomes before retrying. Operators see affected work, interruption cause and continuation actions; architects see usage, availability and configuration. Continuation may use another authorized account, wait for quota recovery or select another method.

## Glossary

- **API key connection:** a named provider binding with holder, access, intake, tools and budgets.
- **Key:** a secret identified by fingerprint; state `active`, `draining`, `disabled` or `retired`.
- **Gateway:** the separate `fleet-gateway` process on PDS18; only it sends provider key values to providers.
- **Snapshot:** coordinator-published token hashes, access lists, provider catalogue and key states; no key values.
- **Spool:** append-only gateway call records ingested by the coordinator.
- **Per-run token:** bearer minted for one execution, removed when the execution ends.
- **Tool:** a provider operation exposed by a connection.
- **`tool_run`, `connection_cost`:** one API call and its usage/cost measurement.
- **`fleet-machines`:** the Access service token used by executors to reach PDS18.

Subscription logins never pass through the gateway. It does not hold or relay OAuth/session credentials. Key switching must not bypass quotas; 429 and quota replies pass through. No Fleet-invented queue bound or rate is added; an owner may configure one per connection. Model API keys as harness endpoints remain a separate, unbuilt integration.

## Technical Plan (Architecture)

Agents reach `fleet-executor mcp connection`, coordinator API steps call HTTP in-process, and both send the execution's token to `fleet-gateway`. The gateway reads the last valid snapshot, attaches the provider key, and appends the call to its spool. The coordinator ingests that record into one accounting execution; caller-supplied labels are not authority.

### 1. Model

*   **`provider`**: a code-side catalogue entry, not a table: `{id, baseUrl, tools: {<tool>: {method, path, unit, idempotent}}}` in `go/coordinator/providers.go`. Tavily exposes `web_search` → `/search` and `web_extract` → `/extract` (unit `credits`, idempotent); Meshy exposes submit and job-read tools. The coordinator copies the catalogue into the snapshot, so the gateway has no second copy.
*   **`api-connection`** document kind (separate from subscription accounts): `{id, name, provider, holder, access: {people: [], projects: [], experiments: []}, intake: all | paused, tools: [], comment}`. **Use:** a run token gets the connection when the run's director, its project or its experiment is listed (any one is enough); `projects: ['*']` means every project; empty means only work directed by the holder. **Visibility** is separate from permission to use a connection; metadata reads follow the normal operation and project scope gates, without exposing key values.
*   **`connection-key`** document kind: `{id, connectionId, fingerprint (first 12 hex of SHA-256), state, addedAt, addedBy, disabledReason?, disabledAt?}`. No value. The key's id is its fingerprint (document id `key:<fingerprint>`), so the gateway's disabled-key file and the spool name keys the same way.
*   The connection carries `holder`; key operations resolve it through `connectionId`, using the same holder/owner and audit model as subscriptions.

### 2. Keys

*   **Values.** `<FLEET_SECRET_DIR>/connections/<connection>/<fingerprint>` on PDS18, one value per file, mode 0600, coordinator user. Added through `connections_key_add` (owner or full-access person only), which writes the file and the metadata row in one step and returns only the fingerprint. Screens, agents, executors and profiles never receive a value.
*   **Key requests.** An agent (a PM session through its Fleet tools, or any execution through the project tool of the same name) calls `connections_key_request {requestId, connection, reason}`. It opens a question of kind `secret` for the owner, with options `{connection}`, idempotent by `requestId`; an agent's question is tied to its execution, so it also shows in that conversation. The owner sees it under Needs you, on its task and in the conversation as a password field with Add key and decline. Add key sends the value from the browser to `connections_key_add {connection, value, questionId}`, which stores it as above and, in the same transaction, answers the question with the JSON text `{connection, fingerprint, state}`; the agent reads that answer with `question_history`. A value Fleet already holds as an active key of that connection answers the request too. Rules: only the owner or a full-access person answers, never an agent, even one acting with the owner's rights; the answer must name an active key; any other answer than `decline` or that fingerprint text is refused, so a typed answer cannot carry a value; the request takes no other argument, so no value rides in it; agents are denied `connections_key_add`; the key row records `addedBy`. The API keys screen (`/keys`, Architect) adds a key without a request.
*   **Import and restore.** At start the coordinator registers every value file that has no row, if the file name matches the value's fingerprint; a directory named after a catalogue provider with no connection becomes that connection (holder owner, access `{projects: ['*']}`). `scripts/connections-import.sh` splits a one-key-per-line file into such files, so import and restore need no database step.
*   **Gateway load.** `fleet-gateway` runs as a user unit of the coordinator user, which already owns the secret directory, so a separate service user would protect nothing. It reads a key's value file when a snapshot first names the key and checks it against the fingerprint; a key change takes effect at the next snapshot adoption, with no restart. Restarts drain in-flight calls while the socket stays open (socket activation).
*   **Backup.** The secret directory is encrypted with SOPS/age into the nightly backup (`fleet-backup.sh`, `secrets.sops.json`; recipient `FLEET_BACKUP_AGE_RECIPIENT` in `backup-age.env`, the age identity kept off the host). To restore, decrypt with the age identity, start the gateway, it serves from its retained snapshot without Postgres.
*   **Rotation:** add → mark old `draining` (no new calls) → `retired` after the owner confirms. Only the owner or a full-access person may re-enable a disabled key; its holder may retire it without re-enabling it. A retired key stays retired. No quiet-period timer (no invented number).
*   **Failover:** to the next active key only when a key got no HTTP answer **and** the tool is `idempotent`. A non-idempotent tool (Meshy submit) returns `outcome: unknown` instead, never replayed. 429 and quota replies pass through unchanged with `Retry-After`. 401 and 402 disable that key (persisted in the gateway's `disabled-keys` file and reported in the spool); a 403 passes through and is recorded on the key as a visible problem with the provider's message, never disabling it, so one bad request body cannot take out the keys one by one (owner decision); if none is left, `503 no-usable-key`.
*   **Reconcile** (Tavily first): every 10 minutes the coordinator asks the gateway's `GET /v1/usage` (loopback, not routed by Caddy, and bearer = the coordinator's per-process usage token whose hash is in the snapshot), which asks the provider per key (catalogue `usage: {path, field}`, Tavily `/usage` `key.usage`). The first answer is the key's baseline; later ones compare the provider's usage since the baseline with the credits recorded for that key's `tool_run` rows since then. A positive difference ("another client uses this key") shows on the key; a failed report shows as unknown, never as a match. Current limitation: a failed gateway request, non-2xx reply or invalid top-level report retains the prior observation without recording the new failure ([tracked correction](https://github.com/taskqorg/fleet/issues/325)); it is not fresh reconciliation proof.

### 3. Gateway

*   **Code.** `go/gateway` is independent of the coordinator and Postgres so coordinator restarts do not stop calls. It provides snapshot adoption, disabled-key persistence, provider error mapping, spool and loss counter:
    *   route `POST /v1/call/<connection>/<tool>`, generic over the provider catalogue;
    *   auth by per-run token hash from the snapshot, without caller-supplied attribution labels;
    *   keys read from the secret directory by fingerprint, so no restart on a key change;
    *   a re-enabled key comes back when the snapshot's `enabledAt` is later than the local disable;
    *   every reply carries `x-fleet-call-id`; a gateway refusal also carries `x-fleet-error` (a passed-through provider reply is `http-<status>` to the client);
    *   no fixed queue bound; a bound is added only when the owner asks for one;
    *   needs-you questions are grouped by cause (people-access §7), for example `key:<id>:disabled`;
    *   budget flags from the snapshot refuse calls with `budget-reached`;
*   **No database on the request path.** The gateway reads `snapshot.json` every second, and once more at once when a call carries a token hash it does not know, before refusing it with `unauthenticated` (this closes the gap between minting and adoption). At most one such reread runs at a time, so junk tokens cannot force a reread storm. The coordinator writes the file atomically on every change of tokens, access lists or key states. A missing or invalid file keeps the last valid one; `/healthz` reports its age. Schema (`GatewaySnapshot` in [`contracts/gateway.schema.json`](../../contracts/gateway.schema.json), one Go type in `go/contract` for the writer and the reader):

    ```text
    {schema: 2, generated_ms, providers: {<id>: {baseUrl, tools, usage?}},
     connections: {<name>: {provider, tools, intake, keys: [{id, state, enabledAt?}], blocked: [<scope>]}},
     tokens: [{sha256, executionId, directedBy, projectId, experimentId, connections: [<name>]}], usageTokenSha256}
    ```
*   **Spool.** `<FLEET_GATEWAY_DIR>/state/spool/<day>.jsonl` (UTC day), append-only; a past day's file is deleted after the coordinator has ingested every line of it; a past day's file with a line that cannot be imported (not a `CallLine`) is kept and logged on each pass, for the owner to inspect and remove. One JSON line per call (`CallLine` in the same contract; absent fields are omitted): `{callId, tokenSha256?, executionId?, connection, tool, keyFingerprint?, status, errorCode?, outcome: ok | error | unknown, usage?: {unit, amount}, disabled?: {key, status}, keyProblem?: {key, status, message}, startedAt, ms}`. The coordinator's in-process call (`api` steps) returns the same type, with `output` (the provider's reply) added. The coordinator ingests it every few seconds (and at step completion) into `tool_run` rows with `connection_cost`. Ingest is idempotent by `callId`; a persistent `lost` counter shows lines that could not be written.
*   **Reach.** Loopback `127.0.0.1:8742` on PDS18. Other hosts call `https://fleet.ufobe.com/v1/call/...`: the Access app "Fleet gateway" (path `/v1/call`) admits only the `fleet-machines` service token, and Caddy sends the path to the gateway, which checks the run token.

### 4. Per-run tokens

*   When dispatch writes the start command, the coordinator mints a random token for the execution, stores its SHA-256 with `{executionId, directedBy, projectId, experimentId, connections}` and republishes the snapshot. The executor receives it in the start command (stored with the command row until the run ends) and writes it, with the gateway URL and the Access file path, to a private run file `<FLEET_DATA_DIR>/runs/<executionId>.env` (0600, in a 0700 directory), deleted when the run ends. Each connection MCP server gets that file's path as its last argument (`fleet-executor mcp connection <name> <spec> <run file>`) and reads `FLEET_RUN_TOKEN`, `FLEET_GATEWAY_URL` and `FLEET_CF_ACCESS_FILE` from it; the harness environment carries none of them.
*   **Threat model.** A token attributes calls per run. It does not isolate runs of one OS user from each other: under FD5 all runs of one harness account share an OS user, so one run can read another live run's environment (`/proc/<pid>/environ`) and call with its token until that run ends. On a held host, the holder can do the same. Both stay within that token's connections, and the holder already sees everything on their host. One OS user per run would close it (data foundation A15 rejected that for now).
*   The token's connections are the profile's granted connections filtered by each connection's `access` list and intake. `projects: ['*']` means all work, with or without a project (Lab runs have none).
*   The coordinator's connection tick (every 3 s) ingests the spool, then marks the tokens of ended executions revoked and republishes the snapshot, so recovery and every other ending path are covered; no separate expiry number. An `api` step's token is revoked right after its call. An execution that ends while the coordinator is down keeps its token until recovery settles it; the first snapshot after that removes it. A grant revocation removes tokens too (people-access §3). Child executions get their own tokens.
*   Coordinator-side `api` steps get a token for their step execution the same way.
*   **Not built: script steps with gateway tokens.** The target gives a token for their step execution the same way, with the profile-free grant set of the pipeline step's `connections` list. The executor writes the same run file and passes its path as `FLEET_RUN_FILE`; the script calls `POST /v1/call/<connection>/<tool>` with it. Each call is a `tool_run` child of the step, so a script that calls the gateway twice records both calls and both costs.
*   **Owner connection tokens.** The owner's own interactive sessions (Claude Code, Codex, Hermes on any host) use a long-lived token from `connections_token_create {name, connections}` (owner and full-access people such as site-agents during development, the minting person recorded as `directedBy`; the value is answered once, with the MCP spec). It lives in a 0600 file named by `FLEET_TOKEN_FILE`, never in a session config. The tick keeps it; `connections_token_revoke` ends it. Its calls are `tool_run` rows with no parent run and `data.tokenName`, directed by the owner.

### 5. Call methods

*   **HTTP:** `POST /v1/call/<connection>/<tool>`, body the tool's JSON, `Authorization: Bearer <run token>`. Replies use (`unauthenticated`, `bad-request`, `no-usable-key`, `key-disabled-<status>`, `provider-unreachable`, `provider-body`, `provider-timeout`; provider status passes through).
*   **Pipeline calls:** the coordinator makes `api` step calls in-process over HTTP with the step's run token. A call answers one `CallLine` (`contract.GatewayCall`, shared with the executor's connection MCP server): `{tool, connection, callId, status, outcome, errorCode?, output}`; error classification (`infra:`/`unknown:`/`step:` problems in fleet-lab.md) stays.
*   **MCP:** `fleet-executor mcp connection <connection> <spec>` (`go/executor/mcp_connection.go`), one stdio MCP server per connection; the start command's `connections: [{name, instructions, tools: [{name, description, inputSchema}]}]` gives the spec, so hosts need no connection files. The executor adds it to each run's MCP config and allowlists `mcp__<connection>__<tool>`, (`go/executor/executor.go`).
*   The gateway spool is the accounting record; an agent-authored local call file is not accounting authority.
*   **Built-in web** stays off unless the profile says `web_route: builtin` (fleet-lab.md R3.4).

### 6. Accounting and budgets

*   Prices for `estimated` money live in the price table ([fleet-analytics.md](fleet-analytics.md#price-table)); a catalogue tool with a fixed vendor price gets its entry with its catalogue entry. A typed-decision provider (yes/no and pick-one answers with probabilities, unit `input_tokens`) is one such catalogue entry.
*   Every call: `tool_run` execution, parent = calling execution, `directed_by` and project copied from the token, plus a `connection_cost` measurement `{connection_id, amount, unit, basis}`. Basis `measured` when the provider returned usage, `estimated` when Fleet computed it from the price table, `subscription` for a subscription run, `unavailable` otherwise ([basis list](fleet-analytics.md#price-table)).
*   Budgets use the shape in people-access §9 with `scope = connection` or with the connection named in a person, project or experiment budget. Spend reaches the coordinator through spool ingest, so a `pause` or `stop` budget can be overshot by the calls made during the ingest delay plus calls in flight, and without limit while the coordinator is down (the gateway keeps the last flags but cannot count). The coordinator computes reached budgets and writes a "blocked by budget" flag per (connection, scope) into the snapshot; the gateway refuses such calls with `budget-reached`, and keeps the last flags while the coordinator is down. Dispatch applies the same budgets to agent runs. `warn` never refuses.
*   Lab usage units are `calls` and `credits`.
*   **Connection budgets.** `budget_set` with `scope: connection` counts that connection's `tool_run` rows: unit `calls`, or the amount of the provider's own unit (`credits`), optionally per `period`. The action is a setting with default `warn` (owner rule outside Lab): `warn` and `pause` show on the budget and the person can ask for more; only a reached `stop` connection budget, set by the owner, becomes `blocked: ['connection']` in the snapshot on the next tick, and the gateway answers `budget-reached`. The gateway also refuses a run whose `person:`, `project:` or `experiment:` scope is listed; person, project and experiment budgets that name a connection are not built yet. `budget_ask {budgetId, limit, reason}` raises one question (`budget:<id>:ask`); only the owner's `approve` writes the new limit, audited with both people.
*   **Meshy.** Catalogue tools `image_to_3d` (not idempotent), `job_status` (`GET .../{jobId}`: a `{field}` in a catalogue path takes that body field) and `recent_tasks`. The job step maps Meshy's task (`status`, `model_urls`, `consumed_credits`) to the job shape; the credits land as `connection_cost` when the task succeeds. Meshy submit has no idempotency key: it is never retried or failed over. On an unknown outcome or 5xx, read the key's `recent_tasks` (`sort_by=-created_at`) and adopt only one matching task created around the call start, not already owned by another execution and with matching image input when the provider returns it. The current matcher allows 5 seconds before the recorded start for clock tolerance. With no matching task, several matches, or unreadable recent tasks, finish `unknown:submit-unconfirmed` and send nothing again. The adopted provider job ID stays in `execution.data.jobId` (the Connections Q1 recovery path).
*   **Asset providers.** Meshy `multi_image_to_3d`, `multi_job_status` and `multi_recent_tasks`; providers `huggingface` (`inference`) and `google-ai` (`generate_content`, key in `x-goog-api-key` by the catalogue's `keyHeader`, usage from `usageField`). Meshy `job_status` and `multi_job_status` report `consumed_credits` when `status` is `SUCCEEDED` (`usageWhen`), keyed by `usageOnce: jobId`; spool ingest counts it once per (connection, job), later polls cost 0, and a pipeline step's job is counted by its step instead. A `{field}` path value is checked against the tool's `pathPatterns` before a key is attached. `scripts/key-add.sh <connection>` sends `connections_key_add` with the value read from stdin only. Keys move from the owner's Mac Keychain this way, csgo tools call the gateway, and each Keychain copy is deleted after the first good call and a backup listing its fingerprint ([asset pipelines §1](fleet-asset-pipelines.md#1-keys-and-providers-s1)).

### 7. Deleting Pipe (stage C4)

Fleet has no Pipe bridge or dual accounting path. The gateway replaces its read lane; subscriptions remain outside it. Deployment cleanup and the archived AssetQ service are covered by [infrastructure](../infrastructure-build.md) and [asset pipelines](fleet-asset-pipelines.md#2-deleting-assetq-s2-after-s1). This heading remains for existing citations; historical rollout tasks live in pull requests.

## Failure and recovery

- Gateway or PDS18 unavailable: calls fail; agent execution may continue without them. A separate gateway avoids coupling calls to coordinator restarts.
- Missing/invalid snapshot: keep the last valid snapshot and expose its age in `/healthz`; new tokens cannot work until adopted. Ended runs may retain tokens while the coordinator is down, until reconciliation publishes revocation.
- Uncertain charged calls are not replayed. Failover requires an idempotent tool and no HTTP answer.
- A spool write failure increments the persistent loss counter. Unimportable past-day records are kept for inspection.
- The same OS user can read another live run's token; see the per-run threat model. Token attribution is not per-run OS isolation.
- Budget overshoot includes ingest delay and in-flight calls, and is unbounded while the coordinator is down.

## Verification

Existing boundary tests are `tests/go/connections.test.ts`, `go/gateway/gateway_test.go` and, for key requests, `PM10` in `tests/go/pm.test.ts`. They protect secret-free replies/snapshots, token attribution/revocation, holder/access gates, failover, usage and spool retention. A provider 403 is recorded on the key and **never disables it**; 401/402 disable it. Tests use fake providers; a docs rework does not call providers or mutate real keys.

Backup encryption is implemented by `deploy/infrastructure/fleet-backup.sh`; a backup listing alone is not a restore proof. A restore check needs the encrypted secret directory and the off-host age identity, then verifies a clean gateway can read its retained snapshot and restored values without Postgres. No restore or production key rotation is implied by editing this specification.

## Not built

- Script-step gateway token provisioning described above.
- Usage reconciliation for Meshy and model APIs; Tavily has the per-key endpoint. Google AI records measured `usageMetadata.totalTokenCount`; Hugging Face usage is unavailable, not zero.
- Person/project/experiment budgets that name a connection, beyond the built connection-scoped budgets and snapshot scope flags.
- Model API keys as harness endpoints; accepting a custom provider base URL and API key is not subscription OAuth support.
