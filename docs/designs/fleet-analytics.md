# Fleet analytics: the work query and the price table

Fleet's analytics is not a subsystem. Experiments, their records, statistics and the comparison screen belong to [Lab](fleet-lab.md#experiment-record); spans belong to [telemetry](fleet-telemetry.md#5-query-surface). This file owns work-history analytics, resource summaries and the price table that turns usage into estimated money.

Status: accepted design; schema, coordinator `analytics_query`, entity resource rollups, and price table built (UI views tracked in [design system](../design-system/README.md)).

## Terms

| Term | Meaning |
|---|---|
| Work record | A leaf `execution` row (`agent_run`, `script`, `tool_run`, or measured `child_agent`) with its `execution_totals` row; container kinds (`pipeline_run`, `pipeline_step`) and placeholder `child_agent` rows without totals are excluded from primary sums. |
| Grouping columns | Typed columns written once when an `execution` row is created: `pipeline_id`, `pipeline_revision`, `step_id`, `profile_id`, `profile_revision`, alongside `project_id`, `kind`, `parent_execution_id`, `harness`, `model`, `host_id`, `experiment_id`, `variant`, `state`, and `started_at`. |
| Basis | How a figure was obtained: `measured`, `estimated`, `subscription` or `unavailable`. |
| Time spans | `elapsed_ms = MAX(ended_at) - MIN(started_at)` across participating leaf executions (turnaround wall span); `execution_wall_ms = SUM(wall_ms)` (parallel effort sum); `cpu_ms = SUM(cpu_ms)` (measured OS CPU time). |
| Price entry | One row of the price table: what one unit of one model or connection tool costs, from one source, on one date. |
| System activity | An execution Fleet makes on its own, not as a project's work: `execution.system_actor` names the component (`coordinator`). See [system activity](#system-activity). |

## `analytics_query`

One operation under the [data foundation §6](fleet-data-foundation.md#6-operations-for-people-and-agents) permission model, for people, the PM agent and the Lab screen (`contracts/ops-analytics.schema.json`). No raw SQL.

**Request.** `{window: {from, to}, dimensions[], measures[], filters{}, projectId?, system?}`. `system` is `exclude` (default), `include` or `only` ([system activity](#system-activity)). The window `[from, to)` (timestamps as epoch milliseconds, RFC 3339, or `YYYY-MM-DD`) is required; there is no default window and no cap on its length.

| Dimensions (fixed list) | Measures (fixed list) |
|---|---|
| `day`, `hour`, `week` (UTC), `project`, `kind` (execution kind), `parent`, `pipeline`, `pipeline_revision`, `step`, `profile_id`, `profile_revision`, `harness`, `model`, `provider`, `account`, `host`, `connection`, `experiment`, `variant`, `state` (final execution state), `outcome`, `person` | `executions` (alias `count`), `count`, `failed` (count in state `failed`), `tokens_input`, `tokens_output`, `tokens_cache_read`, `tokens_cache_write`, `tokens_reasoning`, `wall_ms` (sum), `wall_ms_p50`, `wall_ms_p95`, `active_ms`, `api_ms`, `cpu_ms`, `peak_memory_bytes`, `calls`, `credits`, `cost` |

**Reply.** `{rows, totals, hidden, unknown}`. Each bucket row carries `dimensions` (map from requested dimension name to non-null string, encoding SQL `NULL` / absent dimension values as `"unknown"`), numeric/integer measure structs `{value, basis}` (plus optional `note` / `reason` / `partial` when relevant), and `cost: CostFigure[]` (`{value, currency, basis, prices: [{id, observedAt}], note?, reason?, usages?}`). Reply-level `totals` gives the ungrouped `{measures, cost}` across visible matching rows; `hidden` counts leaf rows inside the unfiltered `[from, to)` window excluded by the caller's row-level security scope (never leaking inaccessible project names, IDs, or spend); `unknown` counts visible matching leaf rows where any requested dimension resolved to `"unknown"` (never dropped).

- A numeric measure that mixes bases reports the weakest one (`unavailable` < `subscription` < `estimated` < `measured`), with `value: null` when completely unmeasured; `peak_memory_bytes` uses `MAX`.
- Cost figures group strictly by `(currency, basis)`: metered charges (`measured` provider cost and `estimated` token tariffs) sum per currency and never combine with `subscription` figures or downgrade metered `basis`; subscription runs keep their own `(currency, "subscription")` list-price equivalent entry (`note: "subscription (list-price equivalent)"`); missing usage or missing prices produce `{value: null, currency: null, basis: "unavailable"}` (never `0`).

**Rules.**

- It runs inside a normal `read: true` transaction under the caller's row-level security (`fleet.project_ids`, `fleet.person`) and never sets `fleet.project_ids` to `'*'` from handler code; non-secret connection provider metadata and aggregate RLS-excluded `hidden` counts (`fleet_exec_conn_meta`, `fleet_window_leaf_count`, `fleet_task_hidden_lineage_count`, `fleet_session_hidden_lineage_count`) execute through narrow SQL `SECURITY DEFINER` helpers. Projectless `directed_totals` access also enforces parent session non-revocation (`NOT (data ? 'directorAccessRevokedAt')`). Agent callers omitting an explicit project filter remain restricted to their bound project(s). A test proves project A sees nothing from project B, including through `score` joins and `tool_run` children.
- Grouping uses the typed columns on `execution` and indexed joins (`project`, `session`, `task`, `account` / `connection`, `price_entry`), never ad-hoc JSON extraction on `execution.data` for grouping columns.
- Nested usage is not counted twice: only leaf executions (`kind NOT IN ('pipeline_run', 'pipeline_step')` and measured `child_agent` rows carrying `execution_totals`) contribute tokens, durations, compute, tools, calls, and cost. Pre-attachment session turns resolve to a task deterministically via `session.data->>'taskId'`. Entity detail views (`task_get`, `session_get`) partition attributed leaf executions into non-overlapping `own`, `delegated`, and `spawned` scopes.
- Per-leaf `LATERAL` price lookup (`FROM price_entry /* served by index price_entry_subject */ WHERE subject = ... AND unit = ... AND effective_from <= leaf_at ORDER BY effective_from DESC, seq DESC LIMIT 1`, where `leaf_at = coalesce(started_at, data->>'startedAt', ended_at, last_seen_at)`) runs inside the leaf CTE **before** outer `GROUP BY` and percentiles, preserving mid-bucket `effective_from` rate changes and exact `(id, observedAt)` provenance.
- `execution(project_id, started_at)` serves the window; rows with null `started_at` fall outside every window.
- Lab descendants inherit `experiment_id` and the trial’s `variant` through their same-project execution parent; `profile_id` remains a separate executor choice. Retained descendants with the old profile-name label are repaired from their typed trial ancestry.
- Native reasoning tokens follow the existing per-call versus final-report token scope. API duration is read only from an explicit final native `duration_api_ms` report, never inferred from wall or active time. Missing observations remain unavailable with a reason; a reported zero remains measured. Retained reports are projected into totals when the schema is upgraded.
- Sources: `calls`, `connection`, `credits`, and money `measured` spend from `tool_run` / `execution_totals.connection_cost`; tokens, durations (`wall_ms`, `active_ms`, `api_ms`, `cpu_ms`), `peak_memory_bytes`, and gateway/harness metrics from `execution_totals`.
- `usage_summary` is not an implemented operation; cost totals come from `analytics_query` and shared `CostFigure[]` rollups. The proposed [`spend_summary`](#spend-view) takes its place.

**Lab use.** The Lab comparison reads trials through the same contract with `experiment` and `variant` as dimensions; the statistics on top are Lab's ([statistics](fleet-lab.md#statistics)).

## Spend view

Requirements for one answer to "where did the agents' money go and what did it buy", for the owner on a Spend screen ([spend](../design-system/pages/spend.md)) and for agents through MCP. Figures come from `analytics_query`; nothing new is stored.

* **Purpose** is a new `analytics_query` dimension, derived per leaf execution in this order: `lab` (it has an `experiment_id`), `task` (it is attributed to a task), `conversation` (a session with no task), `system` (`system_actor` set), else `other`. The screen names them Lab, project work, conversations, Fleet itself and other; research and review agents are told apart by the agent's [library](fleet-definition-editors.md#library) `category`, a second new dimension.
* **Share by purpose:** the [Spend screen](../design-system/pages/spend.md) shows separate distributions of billed USD and estimated USD subscription value. Each uses its own known USD total for the same period and scope. The count of unpriced runs appears beside the total. Bar tooltips show the purpose, amount, and share.
* **What it bought:** per project, tasks completed in the window, the agent spend attributed to those tasks, and cost per completed task. Lab and conversations buy answers, not tasks, and are named as such instead of a per-task figure.
* **By model** (harness and model, runs, cost, unpriced runs) and **by host** (runs, execution wall time, cost).
* **Cost per completed task** against the same project and agent's 30-day median, so an expensive task stands out on Overview and in the task's detail.
* **`spend_summary {window, by: purpose | project | category | profile | model | host, projectId?}`** returns breakdown rows, purpose rows, and scoped totals. The legacy `share` on `rows` and `byPurpose` divides the row's combined known USD amount by the combined known USD total, including measured, estimated, and subscription amounts. It is omitted when either sum is nonpositive.
* **Separate shares for agents.** Use each row's `cost` for the numerator and the same reply's `totals.cost` for the denominator. For billed USD, sum numeric USD figures with basis `measured` or `estimated`. For estimated subscription value, sum numeric USD figures with basis `subscription`. Exclude unavailable figures, null amounts, and other currencies. Report an unavailable share when the row has no matching numeric amount, its basis has no positive total, or its known amount is negative or exceeds the basis total. Keep the recorded amount. Allow floating-point summation error at the upper boundary when it rounds to 100%. An explicit numeric zero divided by a positive total is a known zero. Always use the reply total, including when the returned rows do not add up to it.

## System activity

Fleet's own background calls are observable, attributed to the component that made them, and never counted as a project's work.

- The coordinator reads GitHub (Delivery poll, CI runners screen) and Bugsink (resolution pass) through the gateway with a read token minted for the project whose connection grant allows the read ([connections](fleet-connections.md)). Each call is a `tool_run` with `system_actor = coordinator`. It keeps `project_id`, so row-level security and the grant still decide who sees it, and its connection and tool name what was read.
- `analytics_query`, `executions_list`, project resources (`project_context`, prepared project resources) and person or project budgets leave these rows out by default. `system: include` adds them; `system: only` keeps them alone. A request that names a parent (`executions_list` `parentExecutionId`, `analytics_query` `filters.parent`) and no `system` covers all of that parent's children, so a read token's calls are listed under its id. `hidden` still compares unfiltered windows.
- Connection usage keeps them: connection budgets and the Runners screen (host `coordinator`) count every call on a connection, whoever made it; `analytics_query` with `system: include` and the `connection` dimension gives the same full count. A grouping dimension never changes which rows count.
- `system_actor` is written when the row is inserted, so resource capture needs no trigger on it; migration 69 queues the replacement of the rows it marks. `executions_list {system: only}` reads the partial index `execution_system`.
- Migration 69 marks the rows these reads recorded before the mark (`legacySystemRead` in data): every `tool_run` whose parent is a read token id (`<connection>-read:<uuid>`), and the first reads (2026-11-12), made with a personal token named `github-read` for a project and no person (no parent, `tokenName` in data); a person's own token of that name keeps its calls. Every read token gets the mark too. An hourly pass (`system-reads-cleanup`, first within a minute of start) deletes these rows with their totals (`systemReadsCleanup`), except those a gateway spool line still names, and none while it cannot see the spool: ingest takes a line whose row is missing as new and would replay its key side effects (a refused key disabled again); such a row goes in a later pass, once its spool file is gone. No span names these calls: a gateway call runs under no run context (`telemetry_trace` answers 409 for them), so ClickHouse holds nothing to delete for them.

## Price table

Money is estimated from usage and a price entry. Fleet has no money budget unit; budgets stay `trials | wall_ms | calls | credits`.

**Entry.** `{id, subject, unit, price, currency, source, source_ref, observed_at, effective_from}`.

- `subject`: a resolved model ID (never an alias such as `*-latest`) or `<connection>/<tool>`.
- `unit`: `input_tokens`, `output_tokens`, `cache_read_tokens`, `cache_write_tokens`, or the connection tool's catalogue unit (the same spelling).
- `source`: `vendor` (the vendor's price page, the source of truth), `snapshot` (a fetched public price list, one optional input) or `owner` (hand-entered).
- Entries are append-only; a price change is a new entry. A figure uses the latest entry with `effective_from <= started_at`; none gives `unavailable`. `observed_at` is when the price was read; `effective_from` defaults to it and may be set earlier, so a price entered today can cover past work.

The table belongs to connections and data, beside the provider catalogue in [connections](fleet-connections.md#1-model). A connection with a fixed vendor price per unit gets its entry when its catalogue entry is added.

**Every cost figure** carries its basis, the price entry `id` and its `observed_at`.

| Basis | When |
|---|---|
| `measured` | The provider returned the amount in its own unit (credits or money). |
| `estimated` | Usage × a price entry. |
| `subscription` | The run used a subscription login; shown as "subscription", never as money. |
| `unavailable` | No usage or no price entry. |

The first experiment may use one `owner` entry with basis `estimated`; nothing else is needed before it.

Built: `price_entry`, `price_add`, `prices_list`, typed `CostFigure[]` / `ResourceSummary` / `ScopedResourceRollup` contracts, `analytics_query` with per-leaf `LATERAL` `price_entry_subject` pricing and RLS `hidden`/`unknown` counters, entity rollups in `task_get` / `session_get` / `definition_usage` / `executions_runners` / `lab_experiment_get`. Remaining: public vendor snapshot fetch pipeline and Analytics UI views.

## Prepared project resources

Target: project configuration opens independently of resource accounting. People and agents read the same prepared project summary, with version notifications and lightweight version checks. The latest confirmed facts suffice; no live estimate is required. Newly confirmed facts must reach the visible foreground interface within five seconds of becoming available to Fleet. Observation age and publication age remain separate; missing measurements never become zero.

Source capture, the opt-in contribution processor and additive prepared reads are implemented. The browser selects the prepared path by default when the server advertises it, preserving explicit per-tab opt-out. Production processing and read exposure require qualification and explicit rollout; implementation alone is not live acceptance. Existing `project_context` and analytics reads keep their current query behavior.

### Source ownership and capture

`execution.project_id` is the authority for `execution_totals.project_id`, including NULL. An execution move aligns any existing totals in the same transaction, before source capture. Supported totals writers lock the parent execution row before writing totals; gateway and pipeline cost writers derive ownership from that locked parent, never an old caller-supplied project.

Accepted normalized native usage updates canonical totals while the execution is still running. Existing per-call/final/assistant precedence and replay identities apply. This path does not end an execution or infer wall time, CPU, memory or API duration. Completion and `process.closed` retain their existing process-resource projection.

Execution and totals triggers append durable `resource_work` inside the source transaction. Each work UUID belongs to `(source_xid, execution_id, origin, build_generation, repair_id)`; nullable identity fields compare equal. Repeated writes in one transaction coalesce and retain old/new non-null project scopes. Different transactions keep separate identities, so claiming an earlier row cannot erase a later commit. Source deletion cannot cascade away removal work. `computed_at`, rate-limit-only updates, arbitrary execution JSON and heartbeats with an already fixed leaf time do not create work.

Connection/account classification changes append `resource_metadata_repair` with a stable job identity, first old and last new classification per transaction. Only document ID, kind, provider and normalized connection name are retained; credentials are never copied. Connection `connection:name` matches execution connection `name`; account references match document IDs. Price insertion does not enqueue historical work. Capture stays enabled when processing stops; rollback of a processor must retain pending work.

Work and repair tables are maintenance-only under FORCE RLS. Narrow capture/alignment trigger functions use fixed `search_path`, restore the caller's scope on success/error and expose no unrestricted read or repair operation. A processor must repair legacy execution/totals ownership mismatch before publication.

### Publication contract

The processor has one writer. A replacement transaction may contain every due execution of one pass with one confidently known, non-null project scope, at most 100; it does not wait to fill a cohort. Each extra transaction costs a lock set, summary lock, publication and COMMIT, so smaller cohorts delayed publication under a burst without improving fairness: the single writer serves projects in pass order either way. Moving, NULL, multi-project or uncertain scopes use the independent single-execution path. Canonical source transaction identities and confirmation times remain unchanged.

Each pass selects at most 100 due execution IDs. Starting with the earliest unconsumed candidate, it gathers every eligible ID for that project from the selected set, preserving their relative order even when other projects intervene. An uncertain candidate remains independent. Every selected ID is attempted exactly once through cohort selection before the existing build/metadata pass boundary; failed cohorts retain their bounded independent isolation. Selection does not fetch more work, increase either limit or wait for a full cohort. Earliest-unconsumed priority and per-project order prevent one interleaved project from monopolizing later passes.

Before claiming a cohort, the processor determines the complete sorted project-then-execution advisory-lock set. Under those locks, each leaf independently claims exact immutable work UUIDs and reads canonical facts, old contribution and frozen method in one authoritative statement snapshot. Every actual scope must be covered before support changes; a changed scope rolls back the entire cohort and returns it to the independent path without acquiring a later lock out of order. Source rows are never locked by replacement. Ownership mismatches retain the separate parent-first repair path.

Each leaf retains its own inclusion, unknown/measured-zero/basis/missing reasons and frozen valuation. All applicable subtract/add support, contribution/valuation changes and deletion of only the claimed UUIDs commit atomically. A cohort publishes its project's fixed header/revision and durable wake once after all leaf changes, or publishes nothing when none changes the observable aggregate. One publication may therefore contain several leaves; journal, SSE and API consumers must not assume one leaf per revision. Observation/publication ages and first confirmed source availability stay separate.

Any SQL error rolls the whole cohort back; no healthy leaf is consumed before confirmed COMMIT. A cohort failure attributable to its leaves is retried in halves, so one poison leaf costs about 2·log₂(n) transactions while the healthy rest commits in cohorts (k poison leaves cost at most about 2n); a failure that hits every leaf, such as clearing or cancellation, goes straight to independent attempts; a single remaining leaf takes the independent replacement/backoff path, so a poison leaf cannot indefinitely block healthy work, another project or metadata enumeration. Executions with any captured scope still clearing yield before the bounded candidate limit, retaining their work while other projects advance. An uncertain COMMIT is resolved from retained work UUIDs/contributions/publications before further action; retries never invent work identities or refreeze an already retained valuation. Counted metric/basis support, min/max multiplicities, all tool entries, currency/basis cost groups and price-reference counts still make removals and corrections reversible without a history scan per reader.

One work kit ([`work_kit.go`](../../go/coordinator/work_kit.go)) schedules and retries every item; a failing item pauses on its own and the others keep their pace. An item is an execution's work rows, a project build or a metadata repair. Every failure, before or after the claim, is one guarded write in its own transaction into the item row's `attempts`, `next_attempt_at` and `last_error`: attempts + 1 and the next attempt after base × 2^attempts with up to half a step of seeded jitter added, never above the maximum (there, up to a quarter below it), as client-go's workqueue limiter with `wait.Jitter` does. The defaults are 100 ms and 5 minutes (`FLEET_WORK_RETRY_BASE_MS`, `FLEET_WORK_RETRY_MAX_MS`). The write applies only while what the selection saw is still there: an execution's claimed work UUIDs, a build's generation and update time, a repair's checkpoint; after an uncertain COMMIT that did commit it finds nothing and records nothing. An execution is one item: all its work rows share one attempt count and one pause, so a failure before the claim (a refused lock set) pauses it too, and a new source row neither restarts its count nor makes it a candidate before its pause ends; a success consumes all its rows and a successful build or repair step resets its attempts in the same transaction. A scope the step's hint did not know runs the step again at once, at most three times, then counts as a failure. A busy advisory lock skips the item for that pass without counting. A configured project without a build row is a due build item; its first failure creates the row with its pause. Nothing per item is kept in memory: a queue whose own selection or failure write fails backs off as a whole with the same backoff, so an item whose failure cannot be written retries at the queue's period only until that queue backoff starts. The rules pass reports `resource-failing` (`problem:resource:failing`) while any item's attempts have reached the maximum pause, keeping its open text current, and `work-stalled` (`problem:work:stalled`) while a queue's own bookkeeping has failed that often; it opens and closes both like every rule. These guarantees are executable laws ([design rules](../../go/coordinator/DESIGN_RULES.md)): a poisoned item steps at most log₂(max/base) + T/(0.75·max) + 1 times in time T.

Initial build and metadata scans seed bounded execution-ID pages atomically with their checkpoint. Ready requires scan completion and no scoped pending work/repair in the finalize snapshot. Rebuild retains frozen valuation provenance and source work; incomplete construction stays preparing. First valuation records its method, including missing rates; later price inserts do not automatically reprice historical comparisons.

Prepared reads require a current non-null project grant and matching source ownership. New read operations are additive; legacy operations remain available. Browser integration and load qualification follow server protocol qualification. Synthetic workload results describe their declared history, readers, event rates, hardware and network; they do not establish production capacity. The five-second requirement remains unproved until rendered-value measurements pass under that envelope.

### Processor rollout and internal boundary

`FLEET_RESOURCE_PROCESSOR=on/off` is read once at startup and defaults off. Capture has no off switch: processor-off and restarts retain pending UUIDs. `FLEET_RESOURCE_READS=on/off` is also read once at startup and defaults off. With reads off, the three new operations are not advertised and dispatch returns 503; legacy reads continue. The summary revision trigger writes `resource_summary` with the project ID and a durable wake intent in the same transaction as publication. The change retains its original source XID, actor and permission-filtered scope. A separate always-on dispatcher emits the committed notification hints. Existing XID barriers and reconnect recovery apply; rollback emits no committed change. Internal publication retains the `fleet_resource_summary` channel and project payload. Existing executors, gateway behavior and legacy reads remain compatible.

#### Durable notification delivery

All existing `fleet_change`, `fleet_work` (payload: the work kit queue with new work, `resource-work` or `resource-repair`) and `fleet_resource_summary` producers enqueue maintenance-only wake intents in their canonical transaction. Each append has an immutable UUID, original source XID, exact channel/payload and first enqueue time. Duplicate intents are safe hints; different transactions never contend on a shared queue row. Source work and change rows remain the durable facts. The helper has a fixed search path, validates the channel/payload envelope, temporarily enters maintenance scope only for its append, and restores caller scope on success or error. FORCE RLS prevents scoped readers from observing wake payloads or counts.

One always-on dispatcher per coordinator claims at most 1000 committed intents in enqueue order with `FOR UPDATE SKIP LOCKED`, coalesces equal channel/payload pairs, calls `pg_notify`, and deletes only its claimed UUIDs in one transaction. A failed or interrupted transaction retains every intent and delivers no committed notification. Concurrent enqueues cannot be deleted by an older claim. Full batches continue immediately; an empty/partial batch uses a100ms recovery check, including after startup. This is a qualification parameter, not proof of the five-second visible bound. Runtime resource flags do not disable this dispatcher. Failure spans, claimed count, pending presence and indexed oldest-pending age expose progress without inventing source freshness or scanning the queue for a count on every tick.

Transient notifications do not promise exactly-once delivery. Dispatcher replay may duplicate a hint; listeners read the original committed records under their existing authorization and source-XID visibility barrier. LISTEN reconnect performs catch-up, the resource processor retains its recovery check, and foreground clients retain cheap version checks. A crash after notification commit or a concurrent enqueue at the empty-drain boundary cannot erase source/change history. Dispatcher XIDs never replace source XIDs or become a resource readiness signal. The added delivery delay and journal/processor/browser costs all remain inside the unchanged maximum five-second connected-foreground requirement.

After the outbox migration, the coordinator must include the always-on dispatcher. The supported resource rollback remains processor/read startup flags: capture, intents and dispatch continue. An older coordinator binary without this worker cannot deliver the new intents; source facts remain durable, but that binary alone is not a realtime rollback for this schema.

The [coordinator contract](../../go/coordinator/README.md#internal-prepared-resource-interfaces) defines replacement, ownership repair, build/rebuild, metadata and read helpers. Derived tables enforce FORCE RLS; work and retained valuation are maintenance-only. The internal read helper first reads a scoped header, then checks maintenance progress in the same repeatable-read snapshot. An unfinished metadata enumeration conservatively keeps coverage pending, even before its affected projects are known.

Contributions use canonical typed JSON, sorted metric/tool keys, integer values and decimal strings. Reasoning tokens and reported API duration reach both prepared and shared legacy resource mapping; reasoning is separate from total tokens. Scalar/basis/reason counts and counted extrema preserve measured zero, missing values and partial memory coverage. Normalized tool/cost/price rows have maintained item counts, so the fixed header does not enumerate high-cardinality details.

The first valuation freezes only after confirmed valuation inputs and a usable leaf time/model or connection amount exist; creating a preparing contribution does not choose a method. The frozen method records all token components and the connection unit, including unavailable rates. Later usage corrections reuse it; price insertion alone creates no work. Rebuild clears only disposable contributions/support in bounded pages, keeps source work and valuation, and holds affected replacements while clearing. Initial build and metadata page seeds commit with their checkpoint; an aborted page cannot advance coverage. Failed work keeps its first pending time and retries with delay from 100 ms to one second. Queued hints use retry time before age so failing or clearing scopes do not indefinitely starve others. Completed metadata enumerations waiting on work retain coverage but do not prevent later jobs from scanning.

### Prepared read operations

All three operations require an existing, nonempty non-null `projectId` and current project access. Unknown and revoked projects both return 404; a projectless request returns 400. Project binding applies before item, anchor or cursor interpretation in both agent paths. Derived rows use FORCE RLS with the same project predicate as source ownership. A finer within-project source policy requires an equivalent projection before these reads may serve it; an unsupported visibility scope must fail closed with 409.

- `project_detail` reuses the authoritative project configuration reader, without resource queries. It returns only id, name, content, settings, unknownKeys, context, revision and contentSha; repoSha/sourceState and owner-only initialAccess follow the existing reader conditions. Prepared resource errors do not block configuration reads, and configuration validation errors do not block prepared reads.
- `project_resources` reads a stored fixed-size header, epoch and decimal revision. Its typed reply is `ready`, `unchanged` when knownVersion matches, or `preparing` with version null. Every reply carries progress: initializing/current/updating/error, validatedAt, nullable publishedAt/oldestPendingAt, pending and nullable fixed errorClass. An unchanged publication can still be updating or error. Progress is read after the scoped header through the narrow maintenance helper, in the same repeatable-read snapshot. Its cost does not grow with the project's backlog: each pending scope row carries a copy of its work's first pending time (written with the row and kept equal by triggers) under a per-project index, so the oldest pending age is one index probe; the rare row without a copy is read through a join over its own partial index. Failed work, normally none, is found through its own partial index. Neither a version check nor a missing projection starts a history scan or rebuild.
- `project_resource_items` returns a current atomic header/progress and a bounded tools/costs/prices page, or the same `preparing` variant until a complete header exists. The page has projectId, category, version, items, total, resolvedAnchor and nullable nextCursor/previousCursor. It has no unchanged shortcut: a visible page is revalidated at its current snapshot.

The version is `UUID:decimalRevision`; revisions are strings and are distinct from source progress. Tools carry name, nullable connection, calls and errors. Costs carry nullable currency, basis, nullable value/note/reason/usages and priceCount; prices carry group, priceId and observedAt. The fixed header contains item counts rather than unlimited provenance.

Pages default to 50 items and accept 1..100. Prices require a currency/basis group; other categories forbid it. Only tools accept a case-insensitive literal name query, at most 200 characters. Cursor, start/end anchor and around are mutually exclusive. Sort keys are typed tool (name, nullable connection), cost (nullable currency, basis) or price (priceId, nonnegative integer observedAt); cost/price textual key fields are at most 200 characters. Tool name/connection keys preserve the full admitted source text, including longer native names, so retained rows remain reachable through continuation and deletion-safe re-anchors; the HTTP body bound still applies. Sorting uses PostgreSQL COLLATE C. Keyset continuation never uses OFFSET or enumerates source history.

Cursors encode schemaVersion, projectId, buildEpoch, category, group, query, direction and the complete sort key. They are positions, not authority: authorization precedes parsing and every binding is validated. They bind the build epoch, not its changing revision, so continued publications do not starve scrolling. A replaced epoch returns 409 with restart semantics. Re-anchor using the saved typed tuple: atOrAfter picks the first surviving key at/above it, atOrBefore mirrors that choice, and an empty preferred side picks the nearest survivor on the other side. Active query/group filters apply first. An empty filtered set returns items empty, total zero and resolvedAnchor null. Each page/header is atomic at its own current version; multiple loaded pages are not one historical snapshot.

Large admitted tool keys retain their full display name and connection. When the canonical tool-position JSON exceeds 32 KiB, the tool item also returns optional `position: ResourcePackedToolKey`, and `resolvedAnchor` uses that packed variant. Its shape is `{kind:"tool-position",encoded:string}`. `encoded` is `tp1.` plus unpadded base64url of one complete zlib stream (RFC 1950), whose decoded UTF-8 JSON is `{schemaVersion:1,key:ResourceToolKey}`. The inner key must be an ordinary tool tuple, never another packed position. Clients capture `item.position` when present and otherwise the full ordinary tuple; they must not reconstruct large `around` requests from display text. The same position works after deletion under the active filter, using the nearest-survivor rules.

Small cursor payloads keep the unprefixed base64url JSON form with schemaVersion 1. Above 32 KiB of canonical cursor JSON, the server emits `r2.` plus unpadded base64url of one complete zlib stream containing the same binding fields and full sort tuple, with schemaVersion 2. Readers retain schemaVersion 1 compatibility and require the prefix/schema pair to agree. Compressed positions are not authorization. Project permission is checked first; category, project, group, query, epoch, direction and decoded scalar checks remain unchanged. Revisions do not invalidate either cursor form.

The shared HTTP body limit stays 1 MiB. Encoded positions reserve 4096 bytes inside it for bounded request fields and JSON framing; the server never emits an over-envelope token. Decompression accepts at most `12 * 1 MiB + 4096` bytes: name and connection may each originate from a separate admitted 1 MiB source body, Go JSON can expand each UTF-8 byte up to six bytes (including control characters and `<`, `>` and `&`), and 4096 bytes cover the fixed tuple/cursor framing plus bounded project/group/query fields. This is an allocation bound, not a new tool-name admission cap. Malformed, over-bound, truncated, checksum-invalid or trailing-data streams return 400; truncated decodes are never accepted. Source data is not truncated and the accounting projection is unchanged.

### Browser access and activation

The Projects client selects prepared reads by default when the existing `/api/tools` `tools/list` advertises all three operations. A fresh ordinary `/projects/<id>` needs no special URL or stored selection. Explicit `preparedResources=on/off` is retained for navigation in `sessionStorage` as `fleet-prepared-resources`; `off`, including an existing intentional opt-out, selects the legacy path. Invalid query values do not override a retained opt-out. Storage failure still honors an explicit URL choice and otherwise uses the default. An undeclared/disabled server keeps `project_context`; a later detail dispatch503 falls back to it. This switch changes no coordinator flag. Production activation requires both startup flags, an actual restart/readback, initial build/drain, and authenticated ordinary-path live verification after isolated qualification. Capture remains on throughout.

Configuration, save and revision/content-hash readback use `project_detail`. Header figures and visible breakdown windows use separate shared prepared readers: one in-flight request and one pending refresh per canonical operation/project/request/access-generation tuple. Notifications refresh immediately; foreground checks run at most two seconds apart. The last subscriber aborts and evicts its entry. Same-epoch revisions compare as BigInt; preparing clears unavailable publication data, and unchanged updates progress without erasing figures. Check cadence is not evidence of the five-second bound.

`access.ts` is the sole browser gate authority, without view/api/feed imports. Its order is synchronous invalidation and request abort, identity validation plus cache clear, fresh authorized baseline C, open and synchronous transport activation. Ordinary operations and write retries capture the invocation generation and reject `AccessChanged` across a fence, separately from offline. Only `me` and no-option `changes_since` use the fixed control-call allowlist. Old source/poll/frame callbacks cannot advance cursors or deliver events. A pre-ready or pre-activation change abandons the baseline; failure stays closed and retries through the owned transport/focus path. Focus and coming back online do not fence by themselves: they make a quiet `me` call and fence (invalidate, clear, revalidate) only when the identity or grants version differs, or when the gate is closed; the same person keeps the page and its data, and the change stream brings what happened meanwhile.

Private routed views are generation-keyed and unmounted while validating; non-private shell geometry remains. Module caches and preferences clear synchronously. IndexedDB work checks generation and storage epoch before and after async completion, aborts old transactions and cancels scheduled writes. A blocked deletion after two seconds allows freshly authorized memory only; persistence remains disabled until deletion succeeds. Authored input is separate: Composer adapters and Lab preserve it under its original identity/target, restore only after fresh target authorization, clear server receipts and never automatically resend uncertain writes. Original-text completion cannot erase newer input.

Prepared tools/costs/prices open in the work area with one shared VirtualList scroller, bounded continuous windows, count, tool search and start/end jumps. Refresh captures the shared key/offset, sends the full typed position (opaque packed position when supplied), and restores a surviving key or nearest authorized survivor. A replaced epoch discards cursors and re-anchors. Header and visible page come from one atomic response; loaded windows never claim a historical snapshot. The `data-resource-project`, `data-resource-window`, `data-resource-version` , `data-resource-state`, `data-window-first` and `data-window-last` attributes expose rendered instrumentation without adding operator controls.

Project editor drafts use the same scoped authored-input adapter with separate `project-editor` and `project-create` targets. Existing-project restoration follows a fresh authorized detail read and preserves its base revision/content hash; a changed source becomes an explicit conflict. Shared `AppShell` also fences Spotlight's local private results while preserving column geometry. This extends the browser file inventory to `packages/ui/src/patterns.tsx`, the owner of that private transient state; no new server operation or permission is introduced. Continuous merged windows retain cursors from their actual first/last page; preparing removes local rows/header/cursors.
