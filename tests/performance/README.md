# Interface qualification

`seed-interface.ts` produces synthetic fixture format1/seed1 and an independently enumerated manifest. `interface.ts` runs an isolated coordinator/PostgreSQL and a separate Chromium driver. A fixture, a successful development smoke, a release or CI success is not capacity/live acceptance. The required product behavior is in [prepared project resources](../../docs/designs/fleet-analytics.md#prepared-project-resources).

## Safety and prerequisites

Use task-owned disposable directories/processes, never a production database/origin or another project's data. `serve` creates its own database using `tests/harness.ts`; its PostgreSQL data/socket directory must be inside the specified output directory. Use a short absolute path: Unix socket paths have a platform length limit. Each case needs a fresh server/cluster. The server binds only loopback. Reach it through an SSH tunnel on the separate browser machine; the browser driver rejects non-loopback origins. Its proxy supplies only generated fixture credentials, which never enter output manifests. No agent/model/executor process is launched.

Server: Linux, PostgreSQL15+ binaries on PATH (`initdb`, `pg_ctl`, `psql`), `pg_stat_statements` library, Node22.18+, installed repository dependencies, built candidate coordinator and app. PostgreSQL starts with `track_io_timing`, lock-wait logging and `pg_stat_statements`; `fleet`/`fleet_app` remain non-superuser roles with normal RLS. Only the disposable cluster's local admin enables statistics access. The normal coordinator exporter writes real spans to the fixture's local JSONEachRow capture sink; this does not qualify ClickHouse. No production observability/credential file is read.

Browser: separate reserved Linux machine, installed Playwright Chromium and system libraries. Bound its process resources and preserve host headroom. One context/page per reader, headless Chromium with background throttling disabled, and a verified visible document. No heavy workload on the owner's Mac. `--development` permits only a <=618-row/one-reader/<=3-second smoke and records it as development.

Keep all output under ignored `.egm/` or task-owned remote scratch. The canonical files contain procedures and fixture definitions, never reports or screenshots.

## Placement declarations

Create a private working `server-placement.json` (no credentials):

```json
{"isolatedProfile":true,"vcpu":4,"memoryGiB":8,"ssd":true,"reservation":"task-owned reservation identity","effectiveControls":"observed cgroup paths, cpu.max, memory.max","topology":"actual host/VM/VHDX and physical SSD backing; disclose shared hardware"}
```

Browser `browser-placement.json`:

```json
{"separateMachine":true,"reservation":"exclusive browser reservation identity","effectiveControls":"observed browser cgroup CPU/memory limits","restore":"exact previous idle Fleet-only runner states and restoration command"}
```

Declarations never substitute for readback. `server.json` and `browser.json` record actual CPU/RAM, disk/mounts, cgroup, pressure, PostgreSQL, Chromium, source/diff/binary/bundle identities and network conditions. The original reference is dedicated4-vCPU/8-GiB/SSD Linux plus a separate browser at80ms totalRTT/10Mbps. A reserved cgroup on physically shared hardware or WAN RTT above80ms is an actual alternate profile, not that exact reference; keep original profile coverage untested unless observed. Do not relabel virtual `ROTA=1` as physical HDD or declare SSD without backing evidence.

For the authorized WSL alternate profile, wrap the WHOLE server process tree, including PostgreSQL, in `systemd-run --user --scope -p CPUQuota=400% -p MemoryMax=8G`; read its effective `cpu.max` and `memory.max`. No global WSL settings/shutdown or unrelated service changes. An idle Fleet-only CI guest may be reserved for browser only after confirming runner scope/idle jobs and hosted routing fallback, preserving/restoring its prior state. Never run benchmark coordinator/database load on the production host/CI guest.

## Windows SSH source connection limits

An SSH forwarding endpoint can exhaust its own connection table before the isolated coordinator receives a request. Windows OpenSSH's [compatibility table](https://github.com/PowerShell/openssh-portable/blob/59aba65cf2e2f423c09d12ad825c3b32a11f408f/contrib/win32/win32compat/inc/sys/select.h#L9) has256 descriptor slots per process. Its [socket wrapper](https://github.com/PowerShell/openssh-portable/blob/59aba65cf2e2f423c09d12ad825c3b32a11f408f/contrib/win32/win32compat/w32fd.c#L293) can clear the exhaustion errno, producing `socket: No error` and an SSH `open failed` reply. Verify the actual endpoint/version and failed hop; a browser fetch error alone does not establish this cause.

`relay-interface.ts` provides a task-owned loopback TCP bridge over exactly two independent SSH connections to the same source host. Each accepted stream chooses one source leg in round-robin order and stays on it. The bridge preserves bytes, backpressure and half-close in both directions. It does not replay a flow or move it to another leg after an error. A leg exit fails the relay, closes its active streams and stops both owned SSH children; partial startup and operator cancellation clean up the same children. It changes no global SSH configuration, resource limits, HTTP timeouts, application connection pools or qualification guards.

On the existing relay machine, use two free private loopback ports and the authorized SSH alias for the same source host:

```sh
node tests/performance/relay-interface.ts --host=<source-ssh-alias> \
  --source-port=9479 --listen-port=19493 --leg-ports=19494,19495 \
  > .egm/interface-relay.jsonl 2>&1
```

The outer browser tunnel continues forwarding to loopback19493. The helper starts SSH with independent connections and waits for each child's `LocalCommand` acknowledgement after successful forwarding setup before accepting streams. The command only prints a generated marker; an early SSH listening log or a connection to a possibly foreign listener is not readiness evidence. Retain its ready/leg/flow/terminal metadata and exact helper revision, observe two distinct source SSH child processes and actual stream distribution, and read back the isolated fixture's candidate through the final browser origin. Metadata excludes payloads, credentials and authentication diagnostics. Stop the helper with SIGTERM and verify that its own children, streams and listeners disappear. Reserve these ports for this task; a bind or leg failure stays visible.

Qualify the transport separately: reproduce the single-leg connection refusal with an isolated no-database source and the same declared fanout, then check response identities/completeness through both legs, one-leg exit and partial-start cleanup. A transport regression is not UI capacity acceptance. Record this topology change and all additional hop latency in the original bounds; review earlier evidence reuse against the changed path before resuming the full workload. No transport fix waives an incomplete run, missing render sample, source deadline or maximum5000ms breach.

## Run

Build the exact candidate and retain its identity before copying artifacts to test machines. Go code is unchanged by this runner; a published coordinator may be reused only with verified release-commit/digest identity. Build the candidate app for the default-selection change. Record uncommitted diff identity for development; final qualification must use the accepted exact candidate and its actual binaries/bundle.

```sh
node tests/performance/seed-interface.ts --history=18794 --projects=5 --out=.egm/manifest.json
# Server machine, inside its reserved cgroup; choose a fresh output path/port for each case.
FLEET_TRIAL_PGDATA="$PWD/.egm/case01/pg" FLEET_TRIAL_PGPORT=54379 \
  node tests/performance/interface.ts serve --out=.egm/case01 \
  --placement=.egm/server-placement.json --history=18794 --projects=5 --port=9479
# Browser machine: existing authorized SSH path forwards local9479 to test server loopback9479.
node tests/performance/interface.ts browse --origin=http://127.0.0.1:9479 \
  --out=.egm/case01-browser --placement=.egm/browser-placement.json \
  --readers=10 --rate=20 --network=unshaped
```

The server first seeds with processor off, then actually restarts it on, waits for complete ready/current summaries, and compares stored aggregates to the independent manifest. It adds a running marker actor per project only after baseline parity. The browser opens an ordinary `/projects/<id>` in a clean profile, checks a real Save control and ready figures, measures cold/warm editable state, then opens the actual Tools window. All readers must reach this barrier before writes begin. Each reader remains on one project; simultaneous writes also exercise other projects. Only mounted foreground project/reader pairs claim visible-lag samples. The server logs every confirmed fact, including projects without a mounted reader; those are not fabricated render samples.

Defaults are60-second warmup,600-second sustained phase,1000-change/one-second burst and60-second recovery. `rate` is the requested global source rate, distributed across projects, not per project. Persistent SQL writers avoid spawning a process per fact. Select `browse --source-distribution=hot|distinct` explicitly when comparing results (default `hot`). Hot uses one ordered writer per project and replaces that project's running marker leaf; several captured work hints may coalesce into one replacement. It qualifies hot-execution responsiveness only. Distinct uses eight ordered lanes per project and creates one task-owned included terminal `succeeded` synthetic `agent_run` history arrival and measured tool-call totals per fact, in its own canonical transaction. Distinct scripts are pipelined in their existing FIFO sessions; the hot/native path keeps its previous per-project ordered admission. Each distinct leaf contributes one call and every seventh global fact contributes one failure; no auxiliary marker changes during the distinct source phase. The zero-call marker remains only the initial visible row. Distinct arrivals have explicit synthetic start/end timestamps2024-01-01T00:00:00Z/00:00:01Z; these are fixture history, not actual worker outcomes or measured runtime. Runtime/CPU/API/usage fields remain unknown unless explicitly supplied; no duration is inferred into totals. The hot/native running path is unchanged. Terminal history arrivals do not qualify realistic running/waiting/question load. Keep that separate qualification and any GLOBAL/control contention limitation open; never disable production rules/admission/capture or relabel previous failed runs. The long native fixture is hot-only; use a separate fresh case for distinct. Both modes retain the same requested global schedule and burst; bounded concurrency is recorded as `source-lanes`. Actual source acceptance/commit brackets, schedule delay, burst scheduling duration and backlog reveal whether the requested offered rate was achieved. The common verdict independently requires all sustained and burst facts to be confirmed in distinct transactions, with the entire sustained bracket within its declared duration, each ordered one-second sustained group within one second, and all1000 burst facts within1000ms. Every bracket uses the same server monotonic clock, expanded outward by1ms per endpoint; it includes submission, SQL queueing and commit-receipt overhead. SQL transaction IDs, before-commit database timestamps and after-commit receipts remain raw evidence. Offered scheduling is not admission/commit throughput: inadequate, missing or ambiguous confirmation returns `status: incomplete`, `reason: invalid-source-rate`, even if UI lag passes. This applies to hot, distinct and exceed-capacity; a recovery outcome cannot qualify a source-rate point. Development keeps its shortened declared counts and remains development. A historic hot result reporting1000 offered in999.03ms, confirmed over2475.49ms and UImax851.66ms is source-rate-unqualified; keep its raw evidence and hot classification separately, never reinterpret it as distinct throughput.

All three source phases share one monotonic origin and absolute planned deadlines. The scheduler waits through the full60-second warmup and600-second sustained phase even after the last paced tick. Late work never moves a later deadline or resets the source clock. `source-phase-start/end` and `phaseWindows` retain planned/actual start/end, start/end overshoot and offered counts. Warmup and sustained offer each second's requested facts uniformly over its first800ms, leaving at least200ms planned tail headroom. This versioned schedule is fixed before a run; it preserves every original1000ms window, requested count,600-second horizon and unchanged confirmation validator. Per-fact due/offered/submitted/COMMIT receipts and per-window last planned offer/submission/confirmation plus conservative tail headroom remain evidence. It is not a claim of uniformly spaced confirmations.

The burst is explicitly **early-offered**: all1000 independent facts are offered at the beginning of the original1000ms window. Existing bounded lanes pipeline independent scripts into the same FIFO psql sessions; database transaction concurrency is unchanged. A lane no longer waits for Node receipt processing before accepting its next script. Submission/backpressure queueing stays inside each original source bracket, and only the original tagged post-COMMIT receipt confirms a fact. Scripts are never combined into one transaction or replayed after an error. Process/stdin failure or cancellation rejects every unresolved tag; already received commits remain explicit partial evidence. This is a stronger arrival burst than uniform pacing over that second. Offering is not admission or COMMIT. ALL confirmations, including conservative clock brackets, must fit the ORIGINAL deadline from burst start, not from first submission/COMMIT. No tail/RTT is subtracted and no budget is expanded. The verdict also checks sustained groups against their original one-second windows. Missing phase evidence, inadequate or late confirmation remains incomplete. Development retains its small explicit durations and is never capacity acceptance.

Production serves the app to browsers over HTTP/2 (Cloudflare). `serve --transport=h2` gives the measurement origin the same multiplexed transport: an HTTP/2 TLS server (HTTP/1.1 still accepted) with an ephemeral self-signed loopback certificate written to the case output. Browse it with `--origin=https://127.0.0.1:<port>`; the driver pins the certificate fingerprint of its first answer, requires the fixture to report the same `transport` and certificate, and launches Chromium with `--ignore-certificate-errors-spki-list` for exactly that key, so any other certificate still fails. The coordinator hop stays loopback HTTP/1.1; only connection-specific headers are dropped from HTTP/2 answers. The default `--transport=h1` keeps the HTTP/1.1 origin and its per-origin socket queue, where product reads and the driver's own render receipts wait for the same six sockets per reader. Both runs record `transport`; an h1 result is not an h2 result, and neither is a Cloudflare/Access edge measurement.

For shaped runs use `--network=80ms-10Mbps`: CDP adds80ms latency and caps each reader's upload/download at10Mbps. This is an impairment **in addition to actual network RTT**, not a claim of80ms total. Browser clock probes record the observed shaped round-trip and conservative clock uncertainty; retain unshaped probes too. No firewall/system qdisc is changed. An exact80ms-total profile remains untested if WAN latency already exceeds it.

## Evidence and interpretation

The disposable database keeps a fixture-only committed publication journal. Contribution insert/update/delete deltas and their actual published epoch/revision share the production replacement transaction; rollback leaves no journal publication. The initial qualified snapshot anchors a contiguous history. Missing revisions, unknown versions and epoch resets fail closed. An old painted version is checked against its immutable committed history, rather than whatever version happens to be current when a later proof request runs. This adds measurement work to the isolated database; retain and measure that overhead separately. Journal rows are maintenance-only under forced RLS; the runtime role cannot update or delete committed evidence. The task-owned database is dropped at cleanup. No production schema or capture path is changed.

Record every stable double-animation-frame DOM observation, including its exact version/text, browser clocks and first server receipt before any proof query. Sampling continues while proof requests are pending. Retries keep that same observation and first receipt; every rejected attempt retains its reason. Each reader/fact keeps the earliest proven receipt even before its source receipt arrives; a late older proof corrects an already recorded bound. Raw `render-sample-correction` events retain both observations, and final statistics count each reader/fact once. The receipt remains a conservative render upper bound including outbound observation transport, not an exact first-paint timestamp. A later proof acknowledgement cannot replace it or hide an unknown/missing observation.

`manifest.json` includes deterministic expected inclusion, measured-zero/missing counts, metric sums/present/expected/bases, complete tool calls/errors and separated measured/subscription/estimated money. Seed SQL and expected enumeration do not call production reducers. `parity.json` records the genuine PostgreSQL comparison before measured mutations. Schema/protocol/RLS/frozen-method/restart/cancellation proof is supplied by the exact-artifact predecessor tests; reuse it only when current changes do not invalidate it, and link actual runs. No benchmark prototype substitutes for those assertions.

`source-manifest.json` binds the workload to independent expected execution/tool/failure sums, logical fact IDs, changed leaf IDs/count, canonical SQL mutation counts and commit transaction IDs/count. `manifest.json` remains the unchanged seed baseline. Result JSON repeats the source verdict, expected sample count, observation count and journal rows/bytes. `publication-journal.jsonl` retains complete committed history in bounded export pages; `journal-anchors.json` identifies the initial snapshots. `publication-notifications.jsonl` maps committed publication XIDs to the existing permission-filtered change sequence IDs in bounded post-envelope pages. The browser records native EventSource callbacks without enabling a second all-reader CDP Network event stream. Its constructor proxy delegates to the native constructor with the original arguments/newTarget; credentials, static/prototype behavior, reconnect, custom events, errors and close remain native, and no new connection or HTTP request is created. `eventsource-events.jsonl` retains actual default-message payloads and native open/error events; `notifications-received.jsonl` retains the selected projects' resource-summary messages, including duplicate sequences, exact raw payload and native lastEventId. Untrusted JS-dispatched events are retained as failed capture evidence and never normalized into native notifications. Each record has reader/document/native-instance/open-generation identity, explicit `native-eventsource-callback` provenance and original browser monotonic/wall clocks. These are JS callback clocks, not CDP network arrival or physical TCP connection IDs. Custom events continue to their native application listeners; the recorder does not fabricate them.

The per-document acknowledged FIFO is drained in batches through CDP evidence reads, without HTTP or application updates. Its five-second artifact-drain interval is not a UI refresh or a five-second acceptance claim: source/DOM/firstReceipt endpoints are unchanged. Immutable ordinals distinguish actual duplicates from transport retries. Prefixes are removed only after acknowledgement of successfully written evidence; export keeps complete records under file backpressure. A declared64MiB per-page safety guard never overwrites records: overflow retains a first-lost identity/count and fails capture closed. Parsing, ordinal gaps, missing documents, stream failure and fullness remain incomplete evidence. Cold navigation is frozen/exported before the existing warm navigation; final/failed export retains available data and document/error metadata. Complete artifact names are published only after successful streams, with partial files retained on failure. `api-traces.json` records selected same-origin prepared API trace IDs, header/body timing and actual returned version/state, reusing the original response parse. The fixture adds the supported W3C traceparent header without request interception, extra requests, cache changes or row-content logging. These records correlate with coordinator publication/commit/read spans; an uncommitted version or a later proof acknowledgement is never paint evidence.

`events.jsonl` retains every source bracket, stable render observation, changed-before-paint candidate, proof attempt/rejection, render sample, backlog/control/error and final result.

The visible exact `calls · errors failed` row is rechecked after two animation frames. Its exact epoch/revision/text must match an anchored contiguous publication and that leaf's state at that publication. Hot mode permits a proven monotonic prefix of the same leaf; distinct mode requires exact calls AND errors for the individual included leaf. Neither an aggregate counter nor a newer revision proves a missing leaf. Each reader acknowledges fact IDs individually. Lower timing precedes source submission; upper timing is the first server receipt of that actual painted observation, before proof. Source write/commit and observation-network overhead make this a conservative availability-to-render bound without subtracting an uncertain clock offset. Proof acknowledgement and underlying observation age remain separate. Report min/p50/p95/p99/**max**, every>5000ms sample, missing pairs and errors; empty samples never pass.

`spans.jsonl` retains actual processor batch/replacement/lock timings. PostgreSQL snapshots/statements retain settings, calls/rows/blocks/tempI/O, activity and backlog. Browser observations retain DOM size, long tasks, rendered text, version, visibility and client clocks; screenshots require actual visual inspection. Cold/warm editable and first-summary timings and configuration action acks are diagnostic targets500ms/1500ms/2000ms/300ms as applicable; no percentile replaces the connected foreground maximum5s.

Before accepting a case, inspect generator schedule/actual acceptance rate, server/browser resource/pressure readback, every missing/error/violation, final exact marker parity and drained work. A recovery failure, preparing state or absent browser sample remains failed/pending. Current source does not automatically aggregate a complete cross-case acceptance report; the supervising worker retains exact run coverage and the original-profile limitations.

Stop only this fixture with `POST /__interface/stop` over its loopback tunnel, or SIGTERM the owned server. It stops its coordinator, drops its generated database and stops its own PostgreSQL cluster. Close driver browsers/tunnels, verify scoped process/query disappearance, restore any reserved Fleet-only runner services to their exact previous state and verify their online status. Keep evidence; only task-owned fixture state may be deleted.

Capture never turns off. Production is never this workload runner's origin, and only explicitly task-owned synthetic project data may be changed for live confirmation.

Focused development checks: `tests/go/publication-journal.test.ts` exercises actual canonical source commits and immutable publication history against isolated PostgreSQL: withheld leaf, delayed proof of an old paint, rollback, updates/deletion, replay, history gaps and epoch resets. This outside check runs in CI; it is not a load trial. Pure mode/rate/epoch/order/duplicate/missing/numeric regressions run with `node --test tests/ui/interface-fixture.test.ts tests/ui/publication-proof.test.ts tests/ui/api.test.ts`; `pnpm run app:build`; explicit performance-runner typecheck with the repository TypeScript flags. Full merge gate is CI-only. Small development invocation uses `--development --history=18`, browser `--readers=1 --rate=1 --warmup=0 --duration=3 --burst=1 --recovery=5` and a placement JSON marking development; it is never capacity acceptance.


### Failed finalization and partial browser evidence

Finalization has one owner before any asynchronous wait. Stop cancels further source offering and waits for outstanding writes and the same finalization before closing its private database. Missing source/recovery evidence remains incomplete; known render violations remain failures. A detached result snapshot is published once. Query statistics stream directly from the private PostgreSQL into a `.partial` file with backpressure; only successful process exit and completed output rename it to the complete JSON artifact. There is no1MiB spawn-output buffer. Journal and publication-notification exports also retain `.partial` files until both streams, their database counts and complete-file renames succeed. On any export failure its partial evidence remains: `journalErrors` preserves the original required journal/links error, `auxiliaryErrors` preserves snapshot/statistics errors, and `artifactsComplete=false` across all these mandatory artifacts; an otherwise successful render point is still overall incomplete. This never removes an existing render failure. PostgreSQL stderr diagnostics retain a named tail of at most4096characters; statistics JSON is not truncated.

If the browser cannot obtain final status or complete its normal captures, its `finally` retains available fetch traces in `api-traces-incomplete.json`, actual current pixels in `rendered-incomplete.png` when a page remains, and `browser-incomplete.json` with the original failure, unavailable fields and `visualAcceptance=false`. These artifacts describe that interrupted case; they cannot replace a missing completed screenshot or become capacity/live acceptance. Contexts are then closed. Tests exercise actual>1MiB PostgreSQL output, a held export with concurrent stop/status, a real SQL export exception, cancellation and browser endpoint loss on the18-row development fixture. They are correctness checks, never capacity samples.
