# Protected verifier VM transport, version 1

This is a local verifier-to-broker protocol. It is not a guest attestation or an authorization grant. The verifier connects to the fixed root-managed Unix socket `/run/fleet-design-vm/broker.sock`; the host's socket and directory permissions must admit only the protected verifier unit. The verifier's expected launch identity and runtime are loaded from its root-owned configuration and checked against the signed release build pins. The broker must verify that its independently approved launch manifest binds the golden, BIOS bytes, boot inputs, worker and runtime, execute the pinned VM and return that manifest's SHA-256 only after job exit and teardown. No guest console output can supply that identity or the outer status. This backend is not eligible for production until the binding, guest, runtime, resource and exact-head qualifications pass.

One connection carries one job. All integers below are unsigned big-endian. Byte lengths and SHA-256s are over raw bytes. The broker immediately sends a 40-byte challenge: ASCII `FVMB`, version byte `1`, three zero bytes, then a fresh random 32-byte nonce. The verifier replies with an 80-byte header: `FVMQ` (4), version `1` (1), operation (1), zero (2), nonce (32), payload length (u64), SHA-256(payload) (32), then exactly that many payload bytes. No filenames, executables, shell commands, paths, VM images or user-selected binaries cross this interface.

The broker replies once with a 144-byte header: `FVMR` (4), version `1` (1), operation (1), status (1), zero (1), nonce (32), request payload SHA-256 (32), verified launch-manifest SHA-256 (32), response length (u64), SHA-256(response) (32), then exactly the declared response bytes and EOF. Status `0` means the worker completed and VM teardown was confirmed. Status `1` is a protected, classified BUILD input block; status `2` is unavailable/unconfirmed. Error statuses have an empty payload and carry no provider text. Protocol, identity, timeout and teardown failures are unconfirmed, never a passing check. Extra bytes, an early close, wrong header, wrong nonce, hash, operation, version, identity or unbounded length fail closed.

| Op | Payload | Maximum payload | Success response |
| --- | --- | --- | --- |
| 1 PROBE | empty | 0 | UTF-8 JSON at most 1 KiB: `node`, `chromium`, `guest` (releaseCommit, workerSha256, runtimeSha256) and `runtime` with `imageSha256`, `fontSha256`, `lockSha256`, `node`, `chromium`, `playwright`; all fields must match the protected runtime and signed release pins |
| 2 BUILD | u32 dependency-JSON byte length, dependency JSON, then Git tree tar | 96 KiB dependency JSON and 96 MiB tar | existing build output, at most 24 MiB |
| 3 RENDER | existing fixed renderer JSON | 32 MiB | existing renderer JSON, at most 32 MiB |
| 4 COMPARE | existing two-PNG comparison JSON | 64 MiB plus 2 KiB | existing comparison JSON, at most 1 KiB |

The backend uses one absolute monotonic deadline for connect, framing, work and confirmed teardown, and closes the socket on expiration: 420 seconds for PROBE, 455 for BUILD, 460 for RENDER and 405 for COMPARE. These budgets include up to 60 seconds startup filesystem scan, 180 seconds cold verification of the golden under the 40 MiB/s I/O bound, 30 seconds image inspection, 90 seconds boot, the existing 25/60/65/10 seconds worker window, 30 seconds teardown and 5 seconds transport. The broker must enforce separate boot, existing worker and teardown deadlines, and destroy all VM state on disconnect. BUILD, RENDER and COMPARE require separate protected operator qualification of candidate isolation, request limits and exact-pixel parity; implementing their frames does not qualify them. The stock probe uses the existing 25-second worker deadline inside the guest; the outer deadline also includes boot and teardown.

The root-owned `/etc/fleet-design-verifier/vm-backend.json`, when present, opts in to this backend. It contains exactly `version`, `releaseCommit`, `runtime`, and `launchManifest`; the last field is a JSON string containing the exact bytes of the separately protected broker manifest (including any final newline). The verifier computes its SHA-256 and requires it in each broker response. The manifest contains `version`, `goldenSha256`, `biosSha256`, `releaseSha256`, `guestWorkerSha256`, `runtimeSha256`, and `releaseCommit`; the last must match the issuer's signed release. Probe additionally checks the guest-reported release and measured root-owned worker and runtime against the protected manifest, alongside all runtime pins. These measurements are consistency checks within the separately qualified golden, not hardware attestation. The operator must establish that the approved golden contains the signed guest release and worker. Config cannot select a socket, executable, or image. A missing config retains the local backend; an invalid or inaccessible present config fails closed. Do not enable VM jobs until full qualification.

The guest supervisor sends `FVGR` followed by version byte `1` and three zero bytes only after opening its virtio port. The broker requires this READY within the same 90-second boot deadline before sending a job and starting its worker deadline. Disconnect, timeout, unsuccessful shutdown, or incomplete cleanup gives no successful result.

`isolatedVMJob(operation, payload: Buffer) -> Promise<Buffer>` is the guest supervisor's signed local-worker entry point. It unconditionally checks the local rootfs/runtime against the signed build pins and invokes the fixed bwrap worker; it never reads or selects the VM client config. The guest supervisor maps its `DesignBlocked` to the classified BUILD status and all other failures to unconfirmed. Exact-head visual parity and production qualification are separate gates.

An attempt creates a durable `run.fence.*` work directory before launching any VM. It is removed only after confirmed process, socket, cgroup and scratch cleanup. A cleanup failure stops the broker; the existing startup preflight refuses the retained marker even if socket activation restarts it. An operator must inspect and clear the bounded work directory only after independently confirming that no process or VM remains. Verifier shutdown aborts in-flight broker requests; infrastructure failures mark the renderer unavailable and later polls retry its probe without blocking provider polling.

The optional [designer capture socket](README.md#pds18-broker-binding) uses distinct host authorization and framing. Only that listener can submit internal virtio operation 5. The protected listener retains operations 1 through 4. Operation 5 wraps four length-prefixed files without the permit and carries the bounded `FDR1` reply inside the existing guest response. Capture requires explicit virtio EOF after the guest-shutdown event and clean QEMU exit, before the shared attempt can clear its fence and reply.

While a guest is allocated or cleanup is running, the broker answers the protected listener with a 40-byte `FVBU` record (four magic bytes, version byte 1 and 35 zero bytes). The protected client retries after 250 and 500 milliseconds within its original deadline, then reports renderer busy. A protected caller that receives busy reserves the next idle slot for the protected listener for 45 seconds after clean teardown. The regular 30-second protected verifier retry can use that slot. A concurrent capture receives `FDB1` before it sends its one-use permit. An unconfirmed teardown fences both listeners.

Inside the guest, PID 1 declares the root-only worker socket and starts the finite `User=fleet-render-worker` unit as a boot dependency. The root supervisor opens one socket connection and waits for `FVWK` with version byte 1 and three zero bytes before sending `FVGR` to the host. The local worker accepts only a root peer and one operation byte. Protected operations 1 through 4 consume the already validated payload until write EOF. Operation 5 accepts an empty socket payload and reads only the staged capture input. The local result is status (one byte), size (eight big-endian bytes), bounded output, and EOF. PID 1 powers off after the supervisor terminates. The host still confirms shutdown, QEMU exit, EOF and cleanup before acknowledging capture.
